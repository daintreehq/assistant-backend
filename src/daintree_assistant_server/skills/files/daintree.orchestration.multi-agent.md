Use when: the user wants several agents to collaborate, compete, or cross-check on a single problem, and you are the conductor relaying between them.

The whole pattern is a loop: spawn a cohort → collect each one's output → relay the others' output back to each → ask for the next step → repeat → synthesize one answer. terminal.sendCommand is how you relay. It is always available (every turn, including an autonomous watcher wake) — call it by name, never hunt for it with tool.search.

Procedure:
1. Scope it in one pass. Decide the cohort (which agents — claude, codex, gemini, antigravity, … — resolve any user-spoken name against the roster; a mis-transcribed id launches a dead terminal) and the rounds (e.g. round 1: each answers; round 2: each sees the others and votes). Don't over-plan — the loop is the same regardless of round count.
   - Create ONE scratch store up front as your compaction-safe state carrier: `scratch.create({"name":"multi-agent-orchestration"})`, and hold the returned `storeId` (an `scr_…` handle — there is NO way to list stores, so this handle is the only way back to it). Reuse that EXACT `scr_…` in every scratch.set/get/drop — a mistyped, truncated, or reconstructed storeId fails `SCRATCH_STORE_NOT_FOUND` and writes nothing. Across the whole run you keep the evolving state — the terminalId→role map, the running scores, the round counter, which agent is chronically slow — in ONE key (`orchestration_state`) that you OVERWRITE each round (never a key per round). WHY: a long enough run crosses the auto-compact threshold, and compaction replaces the transcript with a lossy summary that silently drops state living only in prose — leaving the Director quietly unsure who is who. The scratch store lives OUTSIDE the transcript, so it survives compaction. (It is session-only: it does NOT survive a process restart — if the assistant restarts mid-run, re-scope from scratch.)

2. Spawn the cohort in ONE BATCH — one agentTask.spawnForEdits per agent, all emitted together in a single model turn (groups of ~4 per turn), each with a SHORT, self-contained taskPrompt and a distinct `title` so the terminals stay distinguishable. You know exactly what each agent is doing as you spawn it, so NAME IT RIGHT HERE: the `title` becomes the tab name (`<Agent>: <title>`) the instant the agent launches. Do NOT follow the spawn batch with a round of terminal.rename calls — renaming agents you just spawned-and-titled is pure waste; the spawn already named them. (Batched calls dispatch one after another in emission order, not concurrently — the win is the single model turn, not simultaneous execution.) Do NOT attach a watcher (`watch`/`watchGoal`): you are the conductor and you drive the rounds in-turn, so a background watcher here is a SECOND supervisor that fights your driving — the #1 way this task sprawls into minutes of churn and duplicate notifications (the watchers all fire into the inbox AFTER you've already collected and reported, leaving you a pile of redundant items to resolve). Driving in-turn does NOT trap the user: terminal.awaitAll is INTERRUPTIBLE — if they type mid-wait it returns early with `interruptedByUser:true` and their message is already folded into the turn — so you never need a watcher as a "so they aren't blocked" safety net. (If the user instead wants a fire-and-forget "wake me later" run, stop here, attach a watcher, end your turn, and react on the wake — but then do NOT also wait in-turn.)
   - Pick `mode` by what the agents actually do: `mode:"explore"` for thinking/answering/analysis/opinions that touch NO files (the read-only constraint is appended automatically and is task-neutral — it will not contaminate a non-codebase ask); `mode:"edit"` only when they must change files in a worktree.
   - Keep each prompt MINIMAL. State exactly the one thing you want and stop. Do not pad it with extra constraints, codebase instructions, or boilerplate — a bloated or self-contradictory prompt is a top way these tasks go wrong. If you want a fact off the top of its head, say only that.
   - Keep a terminalId→role map. Terminal titles can collide (two "Claude" tabs), so the terminalId each spawn returns is your only reliable handle for routing in step 3. Copy each terminalId EXACTLY and in FULL from the spawn result — a real one looks like `terminal-5284bfef-3d11-424c-90cb-136f24046295`. NEVER abbreviate it to its `terminal-5284bfef` prefix, and never pretty-print or shorten it: Daintree matches the whole id only, so a truncated id matches NO terminal — awaitAll/getStatus then report it "still working" forever and terminal.read returns "Terminal not found".
   - As soon as the spawns return — the SAME turn, before you wait on or relay anything — write the initial state to scratch, so a compaction firing on a later turn can never strand it: `scratch.set({"storeId":"scr_…","key":"orchestration_state","value":{"round":1,"terminalRoles":{"terminal-5284bfef-3d11-424c-90cb-136f24046295":"claude/affirmative","terminal-2e8f0743-b416-4900-816c-297a947874ab":"codex/negative"},"activeTerminalIds":["terminal-5284bfef-3d11-424c-90cb-136f24046295","terminal-2e8f0743-b416-4900-816c-297a947874ab"],"droppedTerminalIds":[],"scores":{"affirmative":0,"negative":0},"slowCounts":{}}})`. The `value` is a raw JSON object — pass it directly, do NOT wrap it in a string. Store each terminalId in FULL exactly as the spawn returned it — never the shortened `terminal-5284bfef` prefix; a truncated id strands every later awaitAll/read against it.

3. Re-anchor from scratch, then wait for the WHOLE cohort. At the TOP of every round, FIRST `scratch.get({"storeId":"scr_…","key":"orchestration_state"})` and restore `terminalRoles`, `activeTerminalIds`, `scores`, `slowCounts`, and `round` from it — after a compaction the transcript may no longer hold them, so the scratch store is your source of truth for who is who and what the score is. Then wait with ONE terminal.awaitAll({ terminalIds: [t1, t2, t3] }), then read their outputs together. awaitAll polls every agent's agentState CONCURRENTLY — no model call, no output read — and resolves when each has gone working→idle (or completed/exited). It is fast and light, but agentState is an IMPERFECT signal: an agent can momentarily read "waiting"/idle while still mid-work (parked before it starts, paused mid-task, or backgrounded). So awaitAll's "finished" is a strong hint, NOT proof.
   - Do NOT issue one terminal.extract wait:{} per agent — that is the SINGLE-agent path and the calls run one after another (three 60s timeouts in a row). One awaitAll for the cohort replaces all of them.
   - VERIFY + SELF-HEAL after awaitAll reports finished: read every agent's output. To pull EACH agent's DISTINCT answer in ONE call, use terminal.extract.json over ALL the terminalIds with a JSON Schema whose value is an array of per-terminal objects, each carrying its own `terminalId` (exact schema in the next bullet) — the multi-terminal tail is labelled `[terminalId]`, so the model attributes each answer to its agent. Do NOT use a plain-text terminal.extract over several ids to collect per-agent answers: a text extract MERGES every terminal's tail into ONE blob, so a singular instruction ("the fact the agent gave") comes back as just ONE fact and you waste a call per agent re-reading them one id at a time. (Plain-text terminal.extract over multiple ids is only for a deliberately BLENDED read; over a SINGLE id it reads that one agent. A bounded terminal.read is fine for one agent's short verbatim answer.) As you read, sanity-check each — if a terminal reported "finished" but its last few lines show it is still working (a half-finished message, a live spinner, no real answer yet), do NOT relay it: re-await just that one, or set a watcher on it and poll, or send a visible agent to look closer. Heal the misread before you synthesize. For garbled multi-screen TUI use terminal.summarize. Don't re-summarize or re-extract an extract result (a model read of a model read). The cohort terminal.extract.json IS the read for the whole round: ONE extract.json over all the terminalIds (an array of `{terminalId, …}`) reads every agent at once, and when it returns matched:true with one entry per agent, those entries ARE the answers (facts/votes/drafts) — go straight to scoring/synthesis. Do NOT follow a successful cohort extract.json with per-terminal terminal.extract calls re-reading the same agents; that re-reads work you already have. This is symmetric across rounds — facts, votes, and drafts are each ONE extract.json, never one extract per agent afterward. If terminal.extract.json fails (502/parse error), fall back to terminal.summarize per agent (one call each) or plain-text terminal.extract per agent — the structured extract is a convenience, not a requirement.
   - Pick the read tool by SHAPE, not by habit. Reading a COHORT (several terminals) into PER-AGENT answers is a terminal.extract.json job: pass an `instruction` AND a `jsonSchema` that is a **real JSON Schema** (only the keywords `type`/`properties`/`items`/`required`/`enum`), with the value an array of objects each carrying its own `terminalId` — e.g. `{"type":"object","properties":{"answers":{"type":"array","items":{"type":"object","properties":{"terminalId":{"type":"string"},"fact":{"type":"string"}},"required":["terminalId","fact"]}}},"required":["answers"]}` (swap `fact` for `vote`/`draft`/whatever the round produced). Do NOT pass an example value shape like `{"answers":[{"terminalId":"string","fact":"string"}]}` — the backend rejects it (`result_schema key 'answers' is not allowed`); it wants a schema, not a sample of the value. ONE call returns one entry per agent, already attributed and ready to tally. Use plain-text terminal.extract (no schema, no "format" arg) only to read a SINGLE terminal, or when you deliberately want all the terminals BLENDED into one answer. Don't plain-text-extract over a multi-id cohort expecting one answer per agent — that is the misread that strands you reading agents one at a time.
   - Suspect a BAD ID before a slow agent. If awaitAll reports the ENTIRE cohort still-working for the whole budget — especially in round 1, right after spawn, when the agents almost certainly finished a quick task in seconds — or a read returns "Terminal not found", do NOT just re-await with a bigger budget assuming slow agents. First suspect a truncated, abbreviated, or stale terminalId: re-read the live ids with terminal.list (or context.snapshot), confirm each id you are using matches a listed terminal EXACTLY and in full (a `terminal-<uuid>`, not a `terminal-5284bfef` prefix), fix any mismatch in your scratch map, then resume with the corrected ids. A whole cohort stuck "still working" for minutes when the work was trivial is the signature of a bad id, not slow agents.
   - Handle the non-finished cases awaitAll reports: the result names them at the top level as `stillWorking` and `askingQuestion` ID arrays, so you can target the stragglers without scanning perTerminal. An agent ASKING A QUESTION → answer the `askingQuestion` ids with sendCommand (step 4) and await again; an agent that FAILED → drop it from the cohort and note it in your synthesis, do NOT respawn in a loop. FAILED covers two shapes: a nonzero exit, AND a terminal awaitAll counted "finished" whose tail, when you read it, shows a CRASH instead of your answer (an error id, "terminated with an error", an empty/garbled screen, no real output — Daintree often reports a CLI that errored on launch as "waiting", so awaitAll mislabels it finished). On a crash: tell the user plainly what happened, re-spawn that agent AT MOST once if they still want it (a fresh terminalId — update your scratch map), and do NOT silently re-spawn it and drop straight back into a blocking await; let the healthy agents proceed. Agents STILL WORKING when the budget ran out → re-await exactly the `stillWorking` ids (not the whole cohort), but BOUND the loop: re-await **at most twice** (three awaitAll calls total on the same terminal). On a re-await you can raise `maxAttempts` (default 30 ≈ 60s, max 240 ≈ 480s) to give a genuinely slow agent more rope instead of looping. Size the await budget UP FRONT too, not reactively after a cap: start round 1 of a multi-round cohort with `maxAttempts:60` (≈ 120s) — the default 30 (≈ 60s) only fits a fast, single-shot cohort. After two re-awaits with no finish the agent is HUNG — stop re-awaiting (never a fourth await on the same id) and take the defined exit: if other agents finished, synthesize from them and note the hung one plainly ("agent `<terminalId>` never finished — omitted from the synthesis"); if the hung agent is the ONLY work left, hand it off to the background and END the turn — publish a blocked inbox item and attach a watcher so the human is woken when it eventually finishes:
   ```
   queue.publish({ "source": "model_worker", "severity": "blocked",
     "title": "Agent hung — did not finish",
     "summary": "Agent <terminalId> still working after 2 re-awaits; attaching a watcher so you're notified when it finishes.",
     "target": { "terminalId": "<terminalId>" }, "dedupeKey": "hung-<terminalId>" })
   watcher.terminal.create({ "terminalIds": ["<terminalId>"], "title": "hung agent recovery",
     "goal": "notify when the stuck agent finishes",
     "stopWhen": { "all": [ { "stateIs": "waiting" }, { "modelJudge": "Has the agent finished its work and stopped, not just paused?" } ] } })
   ```
   Never relay a half-done or dead screen.
   - Remember the straggler ACROSS rounds. Track which terminalId is the lone `stillWorking` entry each round; if the SAME terminal is the only straggler in two consecutive rounds, stop awaiting it inside the cohort. Read the fast agents immediately with a no-wait terminal.extract (they are already idle), then await ONLY the chronic straggler in its own call with a dedicated higher budget (`maxAttempts:120`–`240`). Mechanical reason: a batch dispatches in emission order, so a cohort awaitAll that still includes the slow terminal blocks every read queued behind it — isolating the slow wait lets the fast output flow now instead of at the slow agent's pace.

4. Relay with terminal.sendCommand({ terminalId, command }). Send each agent ONLY what it needs from the OTHERS — their facts/drafts/votes — plus the one question for this round (e.g. "Here are the other two answers: A: … B: … Which is better and why?"). Condense before you relay: the outputs you collected in step 3 are raw material — relay the GIST (a few sentences per agent, clearly labeled by name/role), never raw scrollback. Format relayed answers as `**AGENT_NAME**: <condensed answer>` so a judge agent can attribute and compare. One sendCommand per agent, all in ONE BATCH. Emit the round's terminal.awaitAll as the LAST call in that SAME batch (right after the sendCommands) — dispatch is sequential in emission order, so every send completes and then the await begins, all in one model turn. Issuing the awaitAll in a SEPARATE turn after the sends wastes a full model round-trip every relay cycle. (Exception: once you are isolating a chronic straggler (step 3), the fast agents are already idle — read them straight away with a no-wait extract and give the straggler its OWN dedicated await; don't bundle a cohort awaitAll into the relay batch for agents that already finished.) Then collect again (step 3). Repeat the collect→relay loop for as many rounds as the task needs.
   - If the user sends feedback MID-ORCHESTRATION (via awaitAll's interruptedByUser:true OR as a regular message between rounds), fold it into the next relay — do NOT restart the orchestration. E.g. "be more terse" → append "Keep your answer terse." to the next sendCommand to the relevant agents. Acknowledge the adjustment in one line, then continue the loop.
   - Before you close each round, OVERWRITE the checkpoint with the updated state: `scratch.set` the SAME `orchestration_state` key with the new `round`, `scores`, `slowCounts`, `droppedTerminalIds`, and any gist you'll need next round. Overwriting one key (not a key per round) keeps the key count flat and makes the read-back in step 3 a single get. Keep the WHOLE value compact — well under a few KB: ids, scores, counts, and one-line gists, never raw scrollback or whole agent answers. (A bulky value risks the 10 000-rune cap and gets paged out of the inline result, so keeping it small keeps the read-back a clean single get.)

5. Synthesize and report ONE clean answer — the tally, the winner, the merged result — not a transcript of every terminal. Quote real terminalIds where useful.

6. Close out. Driving in-turn you attach no watchers, so there is usually nothing to cancel; just resolve any inbox item you did create with queue.resolve {"id":"<inbox id>"}. The cohort's terminals stay open and idle — leave them unless the user wants them closed; you can send another round to them anytime with terminal.sendCommand. When the user DOES ask you to close/clean up the terminals, retire the whole cohort in one confirmed call with terminal.close({ terminalIds: ["<id>","<id>",…] }) — don't tool.search for a close tool (terminal.close is always callable) and don't loop it once per id. Close ONLY the exact cohort ids you recorded in your scratch map this run: NEVER include in a terminal.close batch a terminal you did NOT spawn in this run — a pre-existing tab in the dock is very likely the user's OWN working agent, and closing it destroys live work irreversibly. If you are not certain you spawned an id this run, leave it. (Concretely: do not sweep "leftover"/"stale"/"extra" terminals into the close batch as cleanup — only the cohort you created, only on the user's explicit ask.) In a COMPETITIVE workflow (interview, debate, vote), the user may ask to close only the LOSERS while keeping the winner(s) — and any judge — open. Close ONLY the specified losers, not the whole cohort: terminal.close({ terminalIds: ["<loser1>","<loser2>",…] }). Leave the winner(s) open for follow-up work. Drop your scratch store in the SAME cleanup — `scratch.drop({"storeId":"scr_…"})` — so the per-session store budget (20) isn't slowly exhausted across many orchestrations. Keep it while the cohort is alive, though: you may run more rounds against the same state.

Anti-patterns to avoid (these are how this task fails):
- Attaching a watcher AND driving the rounds in-turn — pick one mode (this runbook is in-turn, so NO watcher). Two supervisors on the same terminals is the top cause of churn and duplicate notifications. The "watchers keep the user unblocked" justification is FALSE — awaitAll is interruptible, so the user can redirect mid-wait without a watcher.
- Ignoring an awaitAll that came back with `interruptedByUser:true`. That flag means the user typed mid-wait and their message is ALREADY in the conversation — read and act on it FIRST (they may be changing course) before you re-await or relay anything. Re-awaiting the cohort while their message sits unread is the exact "it won't listen to me" failure.
- Restarting the whole orchestration when the user sends mid-workflow feedback (e.g. "be more terse"). Fold their guidance into the next relay prompt and continue the loop — don't throw away the work already done.
- Silently re-spawning a crashed agent and immediately re-entering a blocking await on it. Surface the crash to the user, re-spawn at most once, and don't re-block the turn on the replacement — let the agents that DID finish proceed.
- Issuing one terminal.extract wait:{} per agent instead of ONE terminal.awaitAll for the cohort — the per-agent waits run one after another and stack their timeouts.
- Spawning the cohort and then immediately renaming the tabs with terminal.rename. The spawn `title` already named each tab (`<Agent>: <title>`) — give each spawn a distinct, descriptive title and skip the rename entirely. Reserve terminal.rename for terminals you did NOT title at spawn (pre-existing tabs, or a fleet whose titles already collide).
- Closing ANY terminal to "recover" from a spawn that failed, came back ambiguous, or returned no terminalId — and closing terminals you did NOT just spawn at all. terminal.close is ONLY ever a response to an explicit user request to close; it is NEVER your own cleanup or recovery move. A pre-existing terminal you didn't create may be the user's own working agent (agentState "working"/"waiting") — closing it destroys live work irreversibly. When a spawn errors or returns no terminalId, READ the terminals (terminal.list) to see state, then re-spawn or report the failure; never close anything to "clear the way". Retire your OWN cohort only when the user actually asks (step 6).
- Padding agent prompts, or appending instructions that contradict the ask. Short and clean wins.
- tool.search-ing for terminal.sendCommand or terminal.awaitAll. They are always callable — just call them.
- A `contains` wait for output the agent already produced (it times out). Wait on the cohort with terminal.awaitAll instead.
- Relaying raw terminal scrollback. Read a FINISHED agent with a batched extract (or summarize), condense to a gist, then relay the gist — never the raw screen.
- Re-extracting each agent individually after a successful cohort extract.json. ONE extract.json over all the terminalIds already returned one attributed `{terminalId, …}` entry per agent — those ARE the answers; follow them straight into scoring/synthesis instead of re-reading the same agents one id at a time. Same in every round (facts, votes, drafts).
- Abbreviating or truncating a terminalId — using `terminal-5284bfef` for `terminal-5284bfef-3d11-424c-90cb-136f24046295`, or rebuilding one from memory. Daintree matches the whole id only, so a shortened id matches no terminal: awaitAll/getStatus then report it "still working" forever and terminal.read returns "Terminal not found". Copy each id in full from the tool result and store it full-length in scratch.
- Assuming "whole cohort still working" (or "Terminal not found") means slow agents. Right after spawn a trivial cohort finishes in seconds — a whole cohort stuck for the full budget is the signature of a bad/truncated terminalId. Re-read live ids with terminal.list and confirm each matches verbatim BEFORE re-awaiting with a bigger budget.
- Including a terminal you did NOT spawn in this run in a terminal.close batch — or closing terminals as "cleanup" of leftover/stale/extra tabs. Close ONLY the exact cohort ids you recorded, ONLY when the user explicitly asked; a pre-existing tab is likely the user's own working agent and closing it destroys live work.
- Relaying on awaitAll's status ALONE without reading the tail — awaitAll is state-based and fast, but idle ≠ guaranteed-done. Self-heal any terminal that reported finished yet still looks busy (re-await or watch it) BEFORE relaying; going on status alone is a top way a round goes out with half-baked output.
- Issuing the round's awaitAll in a SEPARATE turn after the sendCommands — emit it as the LAST call in the SAME batch as the sends so polling starts the moment the sends complete (saves a model round-trip per relay cycle).
- Keeping a chronic straggler inside the cohort awaitAll round after round — once the SAME terminal is the lone straggler in two consecutive rounds, isolate it into its own dedicated, higher-budget await; a cohort awaitAll blocks behind the slow terminal and stalls reading the agents that already finished.
- Re-awaiting the same stuck agent without limit. Bound it to 2 re-awaits, then proceed-without-it (note it) or hand it off to a watcher and end the turn — a genuinely hung agent must never hold the turn open indefinitely.
- Keeping the terminalId→role map, scores, or round counter ONLY in the transcript on a long run — auto-compaction silently discards them and the Director loses track of who is who. Checkpoint them to the scratch store each round (step 4) and read them back at the top of the next (step 3).
- One scratch key per round (`round_1`, `round_2`, …) — use a single `orchestration_state` key and OVERWRITE it every round, so the read-back is one get and the key count stays flat under the cap.
- Storing raw terminal scrollback or string-wrapped JSON in the scratch value — store concise gists, and pass the `value` as a real JSON object, not a string.

Report back: the synthesized result (winner/tally/merged answer), which agents participated (real terminalIds), and any inbox cleanup you did.

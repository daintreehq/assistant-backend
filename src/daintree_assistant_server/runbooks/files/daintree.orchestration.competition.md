---
id: daintree.orchestration.competition
title: Orchestrate a competition or peer-judging among agents
summary: 'Run a scored contest among several named agents: ask each for one independent submission, relay all submissions for blind peer votes, tally the points, and declare the winner or tie — you run the ballot, the agents (or a neutral judge agent) supply the verdict.'
whenToUse: 'Use when the user names several agents (or the fleet) and asks each to produce one independent submission — an interesting fact, a design idea, a quick answer — and then wants them scored: award points, send each agent the others'' submissions, ask each to pick the best, tally, declare a winner. The signal is two-stage: the agents'' OWN submissions become the ballot they peer-judge. A vote over options YOU supplied, even one scored and tallied, is a fleet poll, not a competition. Do not use when each agent instead gets its own unit of real work (daintree.orchestration.fan-out-work), for a judge-led interview (interview runbook), a fleet poll with no scoring (poll-pinned-agents), collaborative debate toward one synthesized answer (multi-agent), a debate that ends by voting a position off (debate-elimination), or a runoff after a tie (runoff-tiebreaker).'
confirmation: "Scoring a contest between the agents. The aim is to rank entries the agents wrote themselves and report who came out ahead, judged on merit rather than on authorship."
risk: project
requiredTools:
  - context.snapshot
  - agentTask.spawnForEdits
  - terminal.awaitAll
  - terminal.await.async
  - async.cancel
  - terminal.read
  - terminal.summarize
  - terminal.sendCommand
  - terminal.close
  - scratch.create
  - scratch.set
  - scratch.get
  - scratch.drop
  - user.askMultipleChoice
---
Use when: the user asks you to run a competition or peer-judging among agents — each produces its own submission, and those submissions become the ballot they judge.

Procedure:
1. Define the independent output each agent must produce (one interesting fact, a design idea) and the judging method — a shortlist plus a peer vote, a peer vote alone, or a neutral judge agent's single verdict (step 4 routes it). Scratch exists to survive COMPACTION, which replaces your transcript with a lossy summary — not to hold what you can already see in it. For a small cohort (roughly 4 or fewer) doing one synchronous round with a single terminal.awaitAll, track the terminalId→agent map, scores and any exclusions directly and verbatim in your own reasoning instead of creating a store. For anything larger, multi-round, or expected to use terminal.await.async, create one up front with scratch.create to hold the terminalId→agent map, activeTerminalIds, omitted/disqualified agents, scores, and any asyncId. Either way, the moment a disqualification, an async wait, a respawn, or a runoff comes up mid-run and you have not started one yet, create it then — exactly the state a later, compacted turn cannot safely reconstruct. If the user gave exact rules (e.g. "the two best get a point each; each peer vote adds one"), follow them mechanically. If no tie rule is specified, default to reporting a tie rather than inventing a tie-breaker.
2. Spawn the cohort in ONE BATCH with agentTask.spawnForEdits, each with a distinct `title` and a short, self-contained `taskPrompt` asking only for that independent output. Build the cohort from your OWN fresh spawns; include an existing terminal only if the user named it. For requested named agents, pass the resolved id as `agentId` on EVERY spawn — omitting it silently launches the default agent, making the cohort N copies of one agent instead of the named field. Supervision: no watchers; a normal quick contest uses one in-turn terminal.awaitAll — on a deliberate terminal.await.async instead, create a scratch store now if you have not already and record its asyncId and covered ids in it. You are the only relay: each taskPrompt asks for the output in that agent's OWN terminal, never routed to or coordinated with another agent. A spawn result IS the launch confirmation — do not spend a round re-listing spawns; go straight to the await. Write the terminalId→agent map and activeTerminalIds — to scratch if you started one, otherwise directly and verbatim in your own reasoning — before the first wait. On a `Terminal not found` or invalid-id error at ANY point in the contest — spawning, awaiting, relaying, collecting votes — suspect the id, not the agent: do not retry the same arguments, and never read it as a question or an exit. Re-verify against the spawn results or context.snapshot, then use the valid id, respawn (only before entries are collected), or mark that agent omitted — in scratch if you have one, otherwise in your own tracking — and report the exclusion. An error like this is itself a reason to start a scratch store now if you have not already.
3. Wait for the whole active cohort with ONE terminal.awaitAll, then read every entry in FREE FORM — one bounded terminal.read per terminal, batched in one turn. Their own words ARE the entries, so never collect entries or votes through terminal.extract / terminal.extract.json — a multi-id text extract merges the cohort into ONE answer, and any extraction paraphrases away the exact wording you are judging — and never ask an agent for JSON. Use terminal.summarize only for garbled multi-screen output — a summary can drop the sentence you need. If awaitAll reports `askingQuestion`, read that terminal before interpreting it — never report a question you have not seen. If the user says an agent is broken, asks to "take it out" or disqualifies it — or its terminal is closed/failed — drop that terminalId from activeTerminalIds — in scratch, or your own tracking — immediately and record it as omitted. If an outstanding terminal.await.async covers that terminalId, async.cancel that asyncId BEFORE claiming the wait will continue, and start a scratch store now if you have not already: an async wait is over the exact original id list, not a live set, may never wake once a member cannot settle, and is exactly the kind of state your own reasoning cannot be trusted to reconstruct after a compaction. Restart the wait with ONLY the remaining active ids, and never wait on, relay to, score a vote from, or re-close a removed terminal again.
4. Route the judgment before you score anything. The ballot is yours — collecting, blinding, relaying, tallying, reporting — but the quality opinion on technical content is not. If the submissions are subjective and non-technical (an interesting fact, a joke, a name, a one-liner), you may pick the top N yourself; say the pick was yours. If they are technical (a design or API idea, an approach, anything code-shaped), do NOT rank them on merit yourself: shortlist ONLY by the user's stated mechanical criterion (meets the stated constraint, inside the stated length, first N to answer), and with no such criterion skip pre-scoring entirely and let the peer vote in step 5 carry the whole result. If the user wants ONE authoritative verdict rather than a peer tally, route it to a neutral judge agent (step 5), never to yourself. Record any points you awarded and the rule you applied — in scratch if you have one, otherwise in your own reasoning.
5. Relay the entries for peer judging on a BLIND ballot. Compile the active agents' outputs; if the rules say a voter receives only the others' submissions, omit that voter's own entry from its ballot, otherwise include all active entries. Strip each entry of author and characterization, give each equal detail, tag them neutrally (Entry 1/2/3 or A/B/C), rotate the tag order per voter so no slot is favoured, and record each voter's tag→agent map — in scratch if you have one, otherwise verbatim in your own reasoning; this map is what de-blinds the report in step 8, so get it exactly right either way. Send each active agent, via terminal.sendCommand, ONLY the neutral list plus: "Judge these on merit. Which ONE is best? Reply with its label (e.g. 'Entry 2') and a one-line reason." Never reveal an author, never mark the voter's own entry as (YOU), never ask for JSON. A voter unknowingly picking its own entry cast a clean merit vote; if self-votes are forbidden, YOU detect it via the map and quietly ask that voter for its next choice, never disclosing authorship. Emit all sendCommands in one batch with awaitAll as the last call in it, and no watcher (an async wait instead follows step 3's active-id rule). If step 4 routed the verdict to a neutral judge agent, spawn exactly ONE in this same batch with agentTask.spawnForEdits (mode "explore", a distinct title, the resolved agentId, no watcher) whose taskPrompt is that same neutral entry list plus the same judge-on-merit question. Its terminalId only comes back after the batch, so it CANNOT be in this batch's awaitAll — await it in step 6. Record it — in scratch if you have one, otherwise in your own reasoning — as the judge, never in activeTerminalIds: not an entrant, no vote, no points. If that verdict replaces the peer tally, send the ballot to the judge only and skip the per-voter sendCommands.
6. Read the votes the same free-form way — one terminal.read per voter terminal, batched, never an extraction over the cohort. Each vote is a neutral tag plus a one-line reason: map the tag back to the authoring agent via that voter's map (scratch, or your own record), and attribute the vote to the voter by terminalId. Do NOT re-read a voter you have already read. If a vote is ambiguous, read that terminal once more; if it is still unclear, send one concise clarification and await only that voter. If you spawned a judge agent, wait for it with ONE terminal.awaitAll over its id and read it the same way; its reply is the verdict, not a vote to tally.
7. Resolve the result. If a neutral judge agent gave the verdict, ITS verdict is the result: report its choice and reasoning as given; if you doubt it, say so to the user as an observation, never as a ranking of your own. Otherwise tally the votes — the top score alone wins, and a tied top score is reported as a tie, never resolved into a sole winner by you. If the user asks for winner-only follow-up while the tie stands (e.g. "close all but the winner"), ask them — user.askMultipleChoice when available — to choose between the tied entrants, co-winners, or a runoff. If they choose a runoff or a new vote, switch to the runoff tie-breaker runbook before cleanup. Until the tie is resolved, keep all tied terminals open and send no sole-winner prompts.
8. Report the tally and winner/co-winners with a synthesis: each agent's output, votes received, and total. Reveal each entry's author HERE, in the report to the user — the blinding applied only to the voters. State who decided (the peer vote, the named judge agent, or your own pick on subjective non-technical entries), and note any removed or failed agent and whether its entry or vote was excluded. If you created a scratch store, clear it with scratch.drop when done — but if the user chose a runoff, hand off with it INTACT instead: the runoff tie-breaker restores the terminalId→agent map, the submissions and the scores from it, or reconstructs them itself if you never created one, and handles its own cleanup.
9. Close terminals only if the user asks. For "besides the winner" cleanup, close ONLY the exact recorded cohort ids that are not a resolved winner — a judge agent's terminal closes with the cohort and is never a winner — and keep every winner/co-winner terminal open. For "close all terminals", close the exact recorded cohort ids plus any pre-existing competition terminal the user named; context.snapshot first if you are unsure what is still open. Finished is not closed: never claim a terminal exited or is already closed without a terminal.close result or context.snapshot proving it. For a winner follow-up such as an acceptance speech, send the prompt only to the resolved winner/co-winner terminals, await and read the replies, and report them.

Confirmation: after closing, confirm which agents were closed and which winner/co-winner terminals remain open.

Report back: the final tally and winner/co-winners, one compact score line per agent, who supplied the verdict, plus any requested winner follow-up or terminal cleanup.

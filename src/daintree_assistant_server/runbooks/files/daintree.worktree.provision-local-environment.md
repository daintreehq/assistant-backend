id: daintree.worktree.provision-local-environment
title: Give each worktree its own database, port and local environment
summary: Diagnose checkouts colliding over one shared database, schema, port, docroot, container or dev server — migrations clobbering each other, a second copy failing to boot, one branch's seed data showing up in another — and get the project's worktree lifecycle setup and teardown scripts written so each worktree provisions its own stack and deleting it releases them.
whenToUse: 'Use for TWO related asks. First, a shared runtime resource that several worktrees collide over so branches cannot run side by side — "my worktrees all share one local site", "each branch needs its own database", "give every worktree its own URL", "two worktrees fight over port 3000". Second, configuring the project''s worktree lifecycle scripts themselves — "add a setup script that runs when a worktree is created", "a teardown script to drop the database when I delete a worktree", "provision new worktrees automatically". The tell is a per-worktree RESOURCE (database, port, hostname, docroot, container) or the setup/teardown configuration that creates it. Do not use to move agents that are already running into separate worktrees (use daintree.worktree.relocate-agents), to create a worktree (use daintree.worktree.create-plain-worktree), to launch a worktree''s startup terminals or dev server (use daintree.recipe.run-or-create), for a cloud devbox or remote resource (use daintree.worktree.manage-resource), or to RUN a test suite, check or command in a worktree that already works (that is an ordinary check run, not a provisioning problem).'
risk: project
requiredTools:
  - worktree.list
optionalTools:
  - worktree.createWithRecipe
  - worktree.waitUntilReady
---
Mostly native file and shell work; the app supplies only `worktree.list` and setup state. A visible agent doing the writing is daintree.edits.spawn-visible-agent, and you still verify its result.

Worktrees isolate code, nothing else. Daintree's answer is lifecycle commands in a `config.json`: `setup` (array of shell commands) runs on create, `teardown` on delete. Daintree takes the FIRST valid file, whole, in order: user-level `~/.daintree/projects/…`, the worktree's `.daintree/config.json`, the main checkout's. Nothing merges; an invalid file is skipped silently. Repository commands run only after the user approves them in Daintree (`needs-approval` until then, and again after edits); user-level commands run without approval. Commands get `DAINTREE_WORKTREE_PATH`, `DAINTREE_WORKTREE_NAME`, `DAINTREE_PROJECT_ROOT` and, when known, `DAINTREE_BRANCH`.

1. Read `worktree.list`. One worktree: nothing collides yet, but configuring setup/teardown is still this job. A clash between two projects is not this problem: say so.
2. Find what exists first: every config location (a user-level file silently overrides the repo's), compose files, env templates, scripts. An existing failing `setup` needs its failure read (`setupState`, `stage`, `error`, then the command's own output), not a new design. `needs-approval` is fixed by the user's approval, never by a manual run or a copy into the user-level file.
3. Split per worktree (database or schema, host or port, docroot, cache prefix, lock and pid files) from shared (read-mostly assets, dependency caches, base images), with a reason each. Derive names from `DAINTREE_WORKTREE_NAME` plus a short path hash; fail rather than fall back to a shared name when a variable is empty. Warn when proposing shared writable state. Ask for what you cannot read.
4. With the user's go-ahead write the scripts where they chose (repo config reaches the team, user-level stays local); otherwise hand over exact content and location. Teardown is required. Setup records what it created in a marker file in the worktree, and a retry adopts or cleans only its own partial resources; teardown releases exactly what the marker names, refuses on a missing or mismatched marker instead of deleting by prefix, and never touches a shared resource. Ask what may be destroyed; export or warn rather than drop data the user may want. Remind them to approve repository commands in Daintree.
5. Prove it on ONE worktree: run setup by hand in its path with the variables, or, if agreed, create one and `worktree.waitUntilReady`. Check the resource exists, the app answers on its own address, and it serves THAT worktree's code: what the running process actually loaded (cwd, docroot target, a branch marker), not an exit 0.
6. Never re-point the shared docroot, symlink or active copy at one branch to make room. Found already switched: report it and name the test results now suspect.
7. Existing worktrees are not provisioned retroactively: list which still need setup run once.

Report back: the collision and worktrees affected; the split with reasons; which config wins; what teardown releases and doesn't; what was written where and by whom; approvals still owed; the worktree verified and the evidence; worktrees still unprovisioned.

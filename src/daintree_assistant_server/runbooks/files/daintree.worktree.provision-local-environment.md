summary: Diagnose checkouts colliding over one shared database, schema, port, docroot, container or dev server — migrations clobbering each other, a second copy failing to boot, one branch's seed data showing up in another — and get the project's worktree lifecycle setup and teardown scripts written so each worktree provisions its own stack and deleting it releases them.

Second, configuring the project''s worktree lifecycle scripts themselves — "add a setup script that runs when a worktree is created", "a teardown script to drop the database when I delete a worktree", "provision new worktrees automatically". Use when: several worktrees of one project need one runtime resource each (a database, port, hostname, docroot, container or dev server) and only one branch can run at a time, or the user wants the project's worktree setup and teardown commands configured.

Availability: Hybrid. The Daintree app MCP supplies the worktree inventory and each worktree's setup state; no app action reads or writes project settings. The rest is native: read the repository and configuration with your file tools, write scripts and configuration when the user asked for that, and run and check commands in each worktree's own path. When the user wants a visible agent to do the writing, use daintree.edits.spawn-visible-agent, and still verify its result yourself.

Worktrees isolate code, nothing else. A second checkout brings no second database, hostname or free port, so parallel agents can each edit a branch while only one can see its result running. Daintree's answer is lifecycle commands: `setup` runs when a worktree is created and `teardown` when it is deleted, so each worktree arrives runnable and takes its resources with it.

How Daintree reads them: a `config.json` holding `setup` and `teardown` as arrays of shell commands, plus an optional `resource` block for remote resources (daintree.worktree.manage-resource). Daintree takes the FIRST valid file it finds, whole, in this order: the user-level project config under `~/.daintree/projects/`, then the worktree's own `.daintree/config.json`, then the main checkout's `.daintree/config.json`. Nothing is merged, an invalid file is skipped without an error, and unknown keys are ignored. Commands from the repository run only after the user approves those exact commands in Daintree (setup reports `needs-approval` until then), and changing them asks again; user-level commands run without approval. The commands get `DAINTREE_WORKTREE_PATH`, `DAINTREE_WORKTREE_NAME`, `DAINTREE_PROJECT_ROOT` and, when known, `DAINTREE_BRANCH`.

Procedure:
1. Confirm the shape. Read `worktree.list` (paths, branches, `setupState`). With one worktree there is no collision to diagnose yet, but configuring setup and teardown for future worktrees is still this job: go on from step 2. A clash between two projects rather than two branches is not this problem: say so.
2. Find what is configured before designing anything. Check every candidate config location above and note which file wins for which worktree: a user-level file silently overrides the repository's. Look for compose files, env templates and existing provisioning scripts. A project that already has `setup` and a failing worktree needs the failure read (`setupState`, `stage` and `error`, then the command's own output when you run it by hand), not a new design. `needs-approval` is not a failure: its fix is the user's approval in Daintree, never a manual run or a copy into the user-level file, which runs without approval.
3. Split per-worktree from shared, with a reason for each:
   - Per worktree, because they collide: the database or schema, hostname or port, docroot or served directory, cache keyspace or prefix, lockfiles and pidfiles.
   - Shared, because copies are waste: large read-mostly assets, dependency caches, base images.
   - Derive per-worktree names from `DAINTREE_WORKTREE_NAME`, the path or the branch, so nothing is edited by hand per worktree. Two branches can sanitize to the same name: add a short hash of the path, and fail rather than fall back to a shared name when a variable is empty. Ask for what you cannot read: which local stack serves the project, and what the user considers safe to share.
   Shared mutable state is a real cost: a branch that rewrites shared uploads or fixtures changes every other worktree. Say so when you propose sharing anything writable.
4. Write the scripts and configuration, or hand them over. With the user's go-ahead, write them where they chose: the repository's `.daintree/config.json` reaches the team through git, and the user-level file stays on this machine. Otherwise give the exact commands, file content and location. Teardown is not optional: a setup that creates a database with no teardown releasing it leaves litter behind every deleted worktree. Make both safe to run twice: setup records what it created in the worktree (for example a marker file naming its database, port and container), and a retry adopts or cleans up only its own partial resources; teardown releases exactly what that marker names, refuses on a missing or mismatched marker instead of deleting by prefix, and never touches a shared resource. Ask what may be destroyed: data the user may want kept is exported or left with a warning, not dropped. Tell the user that repository commands must be approved in Daintree before they run.
5. Prove it on ONE worktree first. Run your new setup by hand in its path with the variables above (a test of the script, not a substitute for the user's approval), or, if the user agreed to a new worktree, create one and wait for `setupState:"ready"` with `worktree.waitUntilReady`. Then check end to end that the resource exists, that the app answers on its own address, and that it serves THAT worktree's code: resolve what the running process actually loaded (its working directory, the docroot's target, or a branch-specific marker), not merely that the script exited 0. A half-provisioned worktree that serves another branch is worse than one that failed outright.
6. Never make room by switching the shared environment over. Re-pointing the shared docroot, symlink or active copy at one branch silently breaks every other agent's results: their tests then exercise the switched-in code. If a worktree cannot be provisioned yet, say it cannot be tested yet. If you find the shared environment already switched, report it before anyone trusts a test result, and name the results now suspect.
7. Close the loop. Worktrees created before the scripts existed are not provisioned retroactively; each needs its setup run once. List which are provisioned and which are not.

Report back: the collision and the worktrees it affected; the per-worktree and shared split with reasons; which config file now wins, what teardown will and will not release, what was written where and by whom (you, the user, or a named agent with its terminal id); any approval the user still has to give in Daintree; the one worktree verified and the evidence; the existing worktrees still unprovisioned.

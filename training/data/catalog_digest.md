# Daintree skill catalog — routing digest
# This is the EXACT projection the production selector sees: {id, summary, whenToUse, foundation}.

## daintree.agents.answer-waiting-agent
title: Answer a waiting agent
summary: Answer a waiting agent’s prompt — one agent, or a whole cohort asking at once — with the exact protocol reply, wait for them to continue, and report the requested results.
whenToUse: Use when one or more already-running visible agents/terminals are waiting on a QUESTION and the user wants them answered — "the agent is asking something, tell it yes", "it's blocked on a prompt", "three of them are waiting on questions, unblock them", "answer the waiting agents and report the result". Includes the fan-out case where several ask at once (terminal.awaitAll returns an askingQuestion array, or the roster shows waitingReason "question"). Do not use when the agent is asking nothing but is hung, silent, or behind a bad terminal id (daintree.agents.recover-agent), for a whole-fleet sweep where answering is only one of several actions (daintree.orchestration.supervise-fleet), to spawn a new agent to ask a question (daintree.agents.ask-and-relay or daintree.edits.spawn-visible-agent), or to poll agents for opinions, votes, or verdicts (daintree.agents.poll-pinned-agents).

## daintree.agents.ask-and-relay
title: Ask an agent and relay its answer
summary: Spawn a configured agent in read-only mode, ask it a question, wait for completion, and report its answer cleanly.
whenToUse: Use when the user wants ONE agent asked ONE question and its answer brought back — "ask claude what it makes of the retry logic", "get an agent to look at the auth module and tell me what it finds", "spawn something to check X and report back". The signal is that the DELIVERABLE IS THE ANSWER, relayed this turn — read-only, one spawn, one in-turn wait, no watcher. Do not use when the deliverable is WORK rather than an answer — implementing, refactoring, fixing, or an investigation the user wants to watch and steer (use daintree.edits.spawn-visible-agent); to poll the pinned or configured fleet (daintree.agents.poll-pinned-agents); for multi-round debate, a scored competition or a judged interview (the relevant daintree.orchestration skill); or when the agent already exists — answer it with daintree.agents.answer-waiting-agent, or use daintree.agents.recover-agent if it has gone wrong.

## daintree.agents.poll-pinned-agents
title: Poll pinned agents
summary: Poll the pinned or configured agent fleet with one neutral question or option vote, read their free-form verdicts, and synthesize a consensus.
whenToUse: Use when the user asks to poll the pinned or configured agent fleet (or several named agents) for independent opinions, votes among options, verdicts, recommendations, or short answers and wants a synthesized consensus. The deliverable is opinions, not work. Do not use when each agent is instead to be given its own unit of real work (use daintree.orchestration.fan-out-work), for a single agent (use the ask-and-relay skill), for multi-round debate or collaboration (use the multi-agent skill), for an open-ended dialogue where the agents talk to each other (use the conversation skill), for a judged scoring competition or interview (use the competition or interview skill), or for breaking a tie (use the runoff tie-breaker skill).

## daintree.agents.recover-agent
title: Recover a broken agent or spawn
summary: Triage an agent that went wrong — read the durable spawn saga, tell a hang from a bad id, and adopt an unsupervised agent instead of restarting it.
whenToUse: Use when something has gone WRONG with an agent or its spawn — "my agent is stuck", "it has been sitting there for ages", "did that agent even start?", "the spawn failed", "nothing happened when you launched it", "that terminal id does not work", "this agent has no watcher on it", "there is an agent running from earlier that nobody is watching", "is it hung or just slow?". Covers a launch that returned no terminalId or an ambiguous result, a hung or unresponsive agent, a stale or mistyped terminal id, and adopting an orphaned or unsupervised agent. Do not use when the agent is healthy and merely ASKING something — answer it with daintree.agents.answer-waiting-agent; for routine triage of a fleet where nothing is broken use daintree.orchestration.supervise-fleet or daintree.orchestration.status-and-resume; to start fresh work use daintree.edits.spawn-visible-agent.

## daintree.agents.relay-review-feedback
title: Relay review feedback to an implementer
summary: Forward review output from one running agent to another with user-specified calibration and optional follow-up instructions.
whenToUse: Use when the user asks you to read one existing reviewer agent's output, review, or notes and point/send another existing implementer agent to it, optionally telling the target how to weigh the source or to report whether the review was useful. The source is a reviewer AGENT's terminal — feedback that must first be fetched from the forge (a PR's review decision, a failing check, an issue thread) is a different job (use daintree.workflow.follow-up-on-issue). Do not use to judge whether the reviewed work is actually done or correct (use daintree.orchestration.verify-agent-work), to spawn a new single agent and ask it a question (use the ask-and-relay skill), to poll several agents for independent opinions (use poll-pinned-agents), or to run multi-round collaboration among agents (use the multi-agent skill).

## daintree.ci.diagnose-and-fix
title: Diagnose and fix a failing check
summary: Take a red test, build or PR check from symptom to verified green — evidence first, fix second, independent verification last.
whenToUse: Use when something is FAILING and the user wants it working — "the tests are failing", "why is CI red", "the build broke", "this check won't pass", "fix the failing test", "is this flaky?" — including the fix-and-verify loop that follows. Do not use to judge the quality of a change that already passes (use daintree.review.review-change), to confirm an agent did what it claimed (use daintree.orchestration.verify-agent-work), to read a PR's review state or comment on its issue without a failure to fix (use daintree.workflow.follow-up-on-issue), to ready a branch for review (use daintree.workflow.prep-branch-for-review), or when the "failure" is Daintree itself misbehaving rather than the project (use daintree.diagnostics).

## daintree.context.curate-copytree-bundle
title: Curate a CopyTree context bundle
summary: Explore the worktree with the read-only fs tools, settle an explicit list of files and patterns, and generate one bounded CopyTree reference file — copying it to the clipboard only when explicitly asked.
whenToUse: Use when the user asks for a curated CopyTree bundle, context bundle, reference file, or clipboard-ready code context for a feature area, subsystem, bug, review, or later handoff — "bundle everything relevant to X, including supporting files and tests". The deliverable is the FILE itself, deliberately selected: explore first, settle an explicit selection, then one generate call. End on copyTree.generate when only the file is wanted; use copyTree.generateAndCopyFile only when the user explicitly asked for the clipboard. Do not use when context is merely an input to launching or feeding an agent — select the workflow that owns the agent instead (daintree.workflow.start-work-on-issue for one issue, daintree.edits.spawn-visible-agent for one new agent, or daintree.orchestration.fan-out-work for injecting context across parallel agents).

## daintree.diagnostics
title: Diagnose a broken or misbehaving Daintree
summary: Work out why Daintree itself is not doing what it should — a dead MCP link, a tool that is not offered, a key that will not sign in — and give the one step that fixes it.
whenToUse: Use when the question is about DAINTREE'S OWN HEALTH — either something is misbehaving and the user wants to know why ("nothing is responding", "the MCP is disconnected", "I did X and nothing happened", "why can't I…", "why is this tool missing"), or they want their SIGN-IN confirmed before they rely on it ("is my key working", "am I actually signed in", "will this burn credit if it is not"). Nothing has to be broken yet for the sign-in case — `daintree.status` reports the MCP link and does NOT answer it, which is exactly why it needs a runbook. Also when they want diagnostics to paste into a bug report. A plain "is Daintree connected?" with nothing reported wrong is a single status read, not this — that is daintree.foundation. Also when a tool you expected is not offered this turn and you must explain why rather than guess a name. Do NOT use for a plain how-to, concept, setting or keybinding question about Daintree ("how do I create a worktree", "what is a watcher", "where do I change X") — the matching documentation is retrieved for you and arrives with the turn already, so answering needs no skill and loading one only spends tokens. Do not use merely because an ordinary working request names Daintree — "rename my tabs" is daintree.terminals.rename — but DO use it when that operation has failed or the capability is missing, including an imperative "it's broken, get it working again", where it may co-load with the operational skill. Do not use for questions about the user's own codebase (use daintree.explore.repository), when a specific agent or spawn has gone wrong (use daintree.agents.recover-agent), to work out where a paused workflow left off (use daintree.orchestration.status-and-resume), or to investigate a red CI check (use daintree.ci.diagnose-and-fix).

## daintree.edits.spawn-visible-agent
title: Spawn a visible agent for edits or exploration
summary: How to handle requests that need a visible agent — to change files or to explore read-only.
whenToUse: Use when the user asks for a direct visible agent to change project files (implement, refactor, fix, add tests, update docs) or to explore/investigate a project read-only, and no more specific workflow applies. Prefer a typed workflow first — daintree.workflow.start-work-on-issue for a forge issue, daintree.workflow.prep-branch-for-review for a PR, daintree.recipe.run-or-create for a workspace recipe, daintree.orchestration.fan-out-work when several independent units each need their own agent, or a poll/competition/interview/multi-agent skill when several agents work together. This is the fallback SINGLE visible-agent path; if the agent is already running and has gone wrong use daintree.agents.recover-agent. If all the user wants is ONE read-only question answered and relayed back — the deliverable is the agent's answer, not work landing — use daintree.agents.ask-and-relay instead. If the deliverable is UNDERSTANDING the codebase rather than changing it, use daintree.explore.repository; if it is a judgement on an existing change, use daintree.review.review-change; if it is a failing test or check, use daintree.ci.diagnose-and-fix.

## daintree.explore.repository
title: Understand a repository
summary: Answer "what does this repo do" / "where is X" with a read-only explore agent and cited evidence.
whenToUse: Use when the user wants to UNDERSTAND the project rather than change it — "what does this repo do", "where is X implemented", "how does the auth flow work", "explain this subsystem", "what would I have to touch to add Y", "find the code that does Z", or orientation before work starts. The deliverable is an explanation with file evidence and nothing on disk changes. Do not use when the user wants files CHANGED (use daintree.edits.spawn-visible-agent, or daintree.workflow.start-work-on-issue for a forge issue), to judge the quality of a specific change or PR (use daintree.review.review-change), to work out why a check is failing (use daintree.ci.diagnose-and-fix), to ask about DAINTREE itself rather than the project (documentation arrives retrieved — no skill needed — or daintree.diagnostics when Daintree is broken), or to pick out files to bundle as context (use daintree.context.curate-copytree-bundle), or when the user names a specific agent to ask and just wants its answer relayed back (use daintree.agents.ask-and-relay).

## daintree.foundation [FOUNDATION]
title: Daintree orchestration foundation
summary: The base judgment under every Daintree workflow — read state before acting, own terminals deliberately, pick one supervision mode, prove a finish, judge even-handedly.
whenToUse: Use for a plain what-exists-right-now read of Daintree state — which terminals, agents, worktrees, branches, queues, timers or watchers exist — and for a single direct control-plane action: reading or focusing ONE terminal, closing ONE the user named, cancelling ONE watcher or async wait, reading whether Daintree is connected when nothing is reported wrong. It is also the DOMAIN FOUNDATION for every daintree.* skill: co-load it with whatever runbook you pick, and load it ALONE only when no runbook squarely matches. Never load it INSTEAD of one that does: triage of running agents is daintree.orchestration.supervise-fleet, "where were we" across sessions is status-and-resume, tearing several things down is workspace-cleanup, leaving something watching past this turn is watch-outcome, retitling tabs is daintree.terminals.rename, and anything REPORTED as broken, unresponsive or missing is daintree.diagnostics; spawning, relaying, competitions, interviews, branch prep and issue work all have their own skill.

## daintree.memory.manage-project-memory
title: Manage project memory
summary: Save, recall, correct, pin and forget durable project facts — without hoarding, duplicating, or storing secrets.
whenToUse: Use when the user asks you to remember something ("remember that we use pnpm", "always run the linter first"), asks what was decided before ("what did we agree about the API shape?", "do you remember why we dropped X?"), wants a saved fact corrected or removed ("forget that", "that's not true any more"), or wants to review, pin or unpin what is stored. Also when you are about to save a fact and should check for an existing one first. Do not use for state that only matters inside this session — a terminal id, a step counter, an in-flight plan (that is the scratch store, per daintree.foundation) — for "where were we?" across sessions (use daintree.orchestration.status-and-resume), or to look something up in the project's CODE rather than in memory (use daintree.explore.repository).

## daintree.orchestration.competition
title: Orchestrate a competition or peer-judging among agents
summary: Run a scored contest among several named agents: ask each for one independent submission, relay all submissions for blind peer votes, tally the points, and declare the winner or tie — you run the ballot, the agents (or a neutral judge agent) supply the verdict.
whenToUse: Use when the user names several agents (or the fleet) and asks each to produce one independent submission — an interesting fact, a design idea, a quick answer — and then wants them scored: award points, send each agent the others' submissions, ask each to pick the best, tally, declare a winner. The signal is two-stage: the agents' OWN submissions become the ballot they peer-judge. A vote over options YOU supplied, even one scored and tallied, is a fleet poll, not a competition. Do not use when each agent instead gets its own unit of real work (daintree.orchestration.fan-out-work), for a judge-led interview (interview skill), a fleet poll with no scoring (poll-pinned-agents), collaborative debate toward one synthesized answer (multi-agent), a debate that ends by voting a position off (debate-elimination), or a runoff after a tie (runoff-tiebreaker).

## daintree.orchestration.conversation
title: Facilitate a live agent conversation
summary: Relay a live back-and-forth conversation among two or more agents, giving each the floor in turn and catching it up on what the others said since it last spoke while you drive the rounds.
whenToUse: Use when the user asks you to facilitate, host, relay, moderate, or keep going a live back-and-forth conversation between TWO OR MORE agents — “get them talking,” “let them talk to each other,” “facilitate a conversation,” “have a group chat/roundtable/panel discussion,” “have the three of them hash it out,” or “see where it goes.” Participant count is just a parameter of this skill. Do not use for a one-shot question to one agent (use ask-and-relay), an independent poll with no cross-talk (use poll-pinned-agents), a judged interview that names a winner (use interview), a scored competition or vote (use competition), a post-tie runoff (use runoff-tiebreaker), a debate that ends by voting a position off (use debate-elimination), or several agents collaborating toward ONE synthesized answer or convergence rather than an open-ended visible dialogue (use multi-agent).

## daintree.orchestration.debate-elimination
title: Run agent debate with elimination vote
summary: Facilitate a multi-agent debate, collect final positions, run a peer vote to eliminate the weakest position, and report the tally.
whenToUse: Use when the user asks several agents to debate a topic and then eliminate, vote off, remove, or identify the weakest agent/position after the debate, including when the elimination request arrives mid-debate. Do not use for a collaborative debate that ends in one synthesized answer with no vote-off (use the multi-agent skill), an open-ended visible conversation among agents with no elimination vote (use the conversation skill), a one-shot independent scored contest or best-entry vote (use the competition skill), a simple fleet poll with no debate (use poll-pinned-agents), or a runoff after a tied vote (use runoff-tiebreaker).

## daintree.orchestration.fan-out-work
title: Fan out disjoint work across parallel agents
summary: Put one agent/terminal on each of several INDEPENDENT units of work — a batch of forge issues, existing issue worktrees, or one goal split into disjoint file-scoped sub-tasks — then supervise the whole fleet in the background.
whenToUse: Use when the user wants several agents each working their OWN separate piece of work at once — take these issues and put an agent on each, an agent per ticket, work the whole batch in parallel, parallelise this across worktrees, knock out the backlog, for each of those worktrees create/open/spawn a new coding-agent or Claude Code terminal in each, run `/work {issue_number}` using the issue number detected on each worktree. The signal is PLURALITY plus INDEPENDENCE — many units, no shared deliverable. Do not use for ONE issue (daintree.workflow.start-work-on-issue) or ONE agent (daintree.edits.spawn-visible-agent); for several agents on the SAME problem converging on one answer (daintree.orchestration.multi-agent) or producing rival solutions to be scored (daintree.orchestration.competition); for opinions rather than work (daintree.agents.poll-pinned-agents); for a fleet that ALREADY exists (daintree.orchestration.supervise-fleet, daintree.orchestration.status-and-resume); or for rescuing one stuck agent (daintree.agents.recover-agent).

## daintree.orchestration.interview
title: Run a judge-led interview competition among agents
summary: One agent interviews several others on a topic while you relay questions and answers — optionally with the judge verifying claims against the codebase and narrowing to a top 2 — until it names a winner.
whenToUse: Use when the user asks to have one agent interview, question, or grill several other agents on a topic and expects a winner — "have one agent interview the others and pick the best", "which of these should be my pair programmer?". Covers both depths, a light Q&A interview and a deep one where the judge verifies candidates' claims against the codebase, issues challenging follow-ups, and narrows to a top 2 before the verdict. Do not use for a plain one-round poll with no interviewer (use the poll-pinned-agents skill), a scoring-only competition where entries are judged rather than questioned (use the competition skill), or an open-ended dialogue with no judge and no winner (use the daintree.orchestration.conversation skill).

## daintree.orchestration.multi-agent
title: Orchestrate multiple agents on one problem
summary: Spawn or use explicitly named open agents, relay their work between them with terminal.sendCommand, and synthesize ONE answer — collaborative multi-agent work driven until the cohort converges.
whenToUse: Use when several agents must work ONE problem together and you relay between them until they CONVERGE on a single synthesized answer — debate until they converge, collaborate, cross-check, iterate toward one merged result. The signal is a synthesis target: the deliverable is the ONE answer you assemble, not a dialogue. Do not use when each agent gets its OWN independent unit of work with no shared deliverable (use daintree.orchestration.fan-out-work); for an open-ended visible dialogue — let them talk, see where it goes (use the conversation skill); a debate that ends by voting a position off (use the debate-elimination skill); independent submissions scored or peer-voted to pick a winner (use the competition skill); a one-shot independent poll (use the poll-pinned-agents skill); or forwarding one agent's review to another (use daintree.agents.relay-review-feedback).

## daintree.orchestration.runoff-tiebreaker
title: Run a runoff tie-breaker for an agent competition
summary: Break a tie in an agent voting competition by getting new submissions from tied entrants, polling the original cohort, and tallying the runoff accurately.
whenToUse: Use when an agent competition, poll, or peer-vote ends in a tie and the user asks for a tie-breaking round or runoff using the same cohort. Do not use to start a fresh competition or poll (use the competition or poll skill), and do not spawn new agents unless the user explicitly changes the electorate.

## daintree.orchestration.status-and-resume
title: Status sweep, ledger hygiene and session resume
summary: Reconstruct what is in flight across turns and sessions from the workflow ledger, live supervisors and session history — then close the stale ledger rows nothing else will.
whenToUse: Use when the user asks where were we, what was I working on, catch me up, what is still open or in flight, what happened while I was away, or to pick up / resume something from an earlier session. Also for the workflow list or ledger itself — why it still shows finished work as active, tidying stale rows, recording a PR onto a row — and for after-the-fact forensics over the audit log. Do not use for a plain what-exists-now read of terminals, worktrees or queues (daintree.foundation), to triage the agents running this minute (daintree.orchestration.supervise-fleet), to set up a watcher or timer that wakes you later (daintree.orchestration.watch-outcome), to verify one agent's output (daintree.orchestration.verify-agent-work), to close terminals or delete worktrees (daintree.orchestration.workspace-cleanup), or to start an issue (daintree.workflow.start-work-on-issue).

## daintree.orchestration.supervise-fleet
title: Supervise a running agent fleet
summary: Triage every agent already running — finished, working, waiting, failed, unsupervised — in one state-only sweep, act on each class, and report what still needs the user.
whenToUse: Use when agents are ALREADY running and the user wants the fleet swept and acted on — "how's everyone doing?", "anything need me?", "is anyone stuck?", "catch me up on the agents". Also for adopting a running-but-unsupervised agent, "show me the next one" navigation, and arming terminals for the user's typed input. Do not use for a plain state read with no action (daintree.foundation), for answering agents that are ASKING (daintree.agents.answer-waiting-agent), for rescuing one broken or hung agent (daintree.agents.recover-agent), for handing out new work (daintree.orchestration.fan-out-work), for "where were we" across sessions (daintree.orchestration.status-and-resume), for proving one agent's work landed (daintree.orchestration.verify-agent-work), for watching past this turn (daintree.orchestration.watch-outcome), or for retitling tabs (daintree.terminals.rename).

## daintree.orchestration.verify-agent-work
title: Verify an agent actually did the work
summary: Test an agent's "done" against evidence — cheap git reads, a small-model verdict on the tail, an explore agent when it needs real inspection — then route on verified, unverified, or contradicted.
whenToUse: Use when the user wants a finished agent's work checked before it is trusted — "did it actually do it?", "check that the agent did what I asked", "verify this before I merge", "it says the tests pass, confirm that", "I don't trust that result" — or when an agent reports done and the next step is irreversible (commit, push, merge, close, hand off). Also to judge a claim against acceptance criteria, or when the tail seems to contradict what the agent said. Do not use to sweep the whole fleet rather than judge ONE result (daintree.orchestration.supervise-fleet), to ready a branch or open a PR (daintree.workflow.prep-branch-for-review), to forward findings to an implementer (daintree.agents.relay-review-feedback), to wait on an agent still running (daintree.orchestration.watch-outcome), for "where were we" across sessions (daintree.orchestration.status-and-resume), or to JUDGE a change on its merits rather than check a claim about it (daintree.review.review-change).

## daintree.orchestration.watch-outcome
title: Watch an outcome unattended
summary: Set up supervision that outlives the turn — a terminal watcher, an async verdict, a PR watch, or a timer — and pre-authorize with a narrow grant when the wake must act.
whenToUse: Use when the user wants to be woken later, not waited on now — "run this overnight and wake me", "let me know when the build finishes", "ping me when the PR merges", "remind me in an hour", "keep an eye on it while I'm out" — or any request to leave something watching after this turn. Also to pre-authorize an unattended action with a grant, and to list, cancel or revoke watchers, timers, async waits and grants you left. Do not use to cancel ONE named watcher (daintree.foundation), a one-off check of an agent that already finished (daintree.orchestration.verify-agent-work), triage of what is running now (daintree.orchestration.supervise-fleet), what happened while you were away (daintree.orchestration.status-and-resume), or wholesale teardown (daintree.orchestration.workspace-cleanup). `watcher.watchPR` sees only a PR's open/merged/draft/closed state, so a one-off read of CI, checks, reviews or an issue thread is not a watch at all (use daintree.workflow.follow-up-on-issue).

## daintree.orchestration.workspace-cleanup
title: Tear down a workspace safely
summary: The confirmation gate for teardown — inventory, classify safe/unsafe/unknown, get an explicit go-ahead, then cancel supervision, close terminals, delete worktrees and settle the ledger in dependency order.
whenToUse: Use ONLY when the user explicitly asks to tear down workspace state after a fan-out, competition or long session — "close these", "clean up", "tidy up the terminals", "shut it all down", "disarm everything", "delete that worktree", "mark those workflows done". A cleanup request in the user's own words is required; never select this for a status question, and never treat it as permission to close anything on your own initiative. Do not use for closing ONE named terminal or cancelling ONE watcher (daintree.foundation covers that), to cancel or revoke supervision with nothing else torn down (daintree.orchestration.watch-outcome), to triage or check on a running fleet (daintree.orchestration.supervise-fleet), to answer "what is running" or "where were we" (daintree.orchestration.status-and-resume), or to judge whether an agent's work is good (daintree.orchestration.verify-agent-work).

## daintree.recipe.run-or-create
title: Run a Daintree workspace recipe, or create a worktree with one
summary: List, inspect and run an EXISTING Daintree workspace recipe — or create a worktree with one as its startup recipe — then supervise any LIVE agent it spawns. Nothing here authors or edits a recipe.
whenToUse: Use when the user asks to list, inspect, load, run or apply an existing Daintree workspace recipe, or to create a worktree with a startup recipe. Also use when they ask to CREATE or edit a recipe — only so you can say plainly that no tool can author one and offer what you can actually do. Do not use to create a worktree for a forge issue, which has its own typed workflow (use daintree.workflow.start-work-on-issue), to launch a single agent with no recipe involved (use daintree.edits.spawn-visible-agent), or to delete a worktree and tear the workspace down (use daintree.orchestration.workspace-cleanup).

## daintree.review.review-change
title: Review a change
summary: Review a diff, branch or PR with independent read-only reviewers, and return de-duplicated findings with file evidence.
whenToUse: Use when the user wants a change JUDGED on its merits — "review this", "code review the branch", "is this PR any good", "check this for security problems", "what would you change about this diff", "look over what the agent wrote". The deliverable is FINDINGS with severity and file evidence. Do not use to check whether an agent did what it claimed before you trust it (use daintree.orchestration.verify-agent-work — that asks "is the claim true", this asks "is the change good"), to ready a branch or open a PR (use daintree.workflow.prep-branch-for-review), to forward findings you already have to an implementer (use daintree.agents.relay-review-feedback), to explain how existing code works (use daintree.explore.repository), or to fix a failing check (use daintree.ci.diagnose-and-fix), or when the user names a specific agent to ask and just wants its answer relayed back (use daintree.agents.ask-and-relay).

## daintree.terminals.rename
title: Rename terminal tabs
summary: Give terminals/agents clear tab titles — the fast, direct route (no tool hunting).
whenToUse: Use whenever the user wants to rename terminals/tabs, retitle agents, or "figure out what each of these terminals is doing and give them a title" — especially when several agents share the same name (e.g. all "Claude") and need to be told apart. The deliverable is new TITLES. Do not use when the user wants a report on what the agents are doing rather than a retitle (use daintree.orchestration.supervise-fleet), a plain list of what terminals exist (use daintree.foundation), or an explanation of HOW renaming works rather than the rename itself (that is a documentation question — the pages arrive retrieved and no skill is needed).

## daintree.workflow.find-issue-work
title: Find forge issue work
summary: Search the issue tracker with a provider-native query, then screen the hits against work already in flight so the shortlist only contains issues nobody has started.
whenToUse: Use when the user wants to FIND issues rather than start one — search or filter the tracker, triage the backlog, "what should I pick up next", "anything unassigned", "find me a small bug nobody's on" — or to check whether an issue is already being worked before committing to it. The deliverable is a shortlist or one chosen issue, NOT a launched agent. Do not use once the issue is chosen and the user wants it started (use daintree.workflow.start-work-on-issue); to launch a batch of issues in parallel, one agent each (use daintree.orchestration.fan-out-work); to reconstruct what was already running across earlier sessions (use daintree.orchestration.status-and-resume); or to read an existing PR's CI, review state or issue thread (use daintree.workflow.follow-up-on-issue).

## daintree.workflow.follow-up-on-issue
title: Follow up on a forge issue
summary: Read where an issue actually stands right now — its PR, the CI roll-up, the review decision, the comment thread — then relay what is blocking it, or comment and close it out.
whenToUse: Use for a one-off READ of an issue or PR's current forge state and the writes that close it out — "is that PR green?", "did CI pass?", "what's blocking it?", "did anyone reply on that issue?", "what did the reviewer say?", "comment on it and close it". Covers checking CI or check status, reading a review decision, reading an issue's comment thread, forwarding forge-sourced blockers to the agent still working, and posting a closing comment. Do not use to leave something watching and wake the user on a LATER PR transition (use daintree.orchestration.watch-outcome); to commit, push, open or ready a PR (use daintree.workflow.prep-branch-for-review); to search or triage the backlog for new work (use daintree.workflow.find-issue-work); to start work on an issue (use daintree.workflow.start-work-on-issue); or to forward a review that is already sitting in a reviewer agent's terminal rather than on the forge (use daintree.agents.relay-review-feedback). Do not use to DIAGNOSE or FIX a failing check — reading that a check is red is here, working out why and getting it green is daintree.ci.diagnose-and-fix.

## daintree.workflow.prep-branch-for-review
title: Prepare a branch for review
summary: Get a read-only review-readiness verdict, then do the real prep — commit, push, open the PR — branching on what the verdict reports.
whenToUse: Use when the user asks to prepare a branch for review, open or ready a PR, wrap up work on an issue for review, or check whether the current branch is ready to push. Do not use to judge whether an agent's work is actually correct or complete before trusting it (use daintree.orchestration.verify-agent-work), to START work on an issue rather than finish it (use daintree.workflow.start-work-on-issue), to be notified later when the PR merges (use daintree.orchestration.watch-outcome), to read an EXISTING PR's CI or review state or to comment on and close its issue (use daintree.workflow.follow-up-on-issue), to forward a reviewer's findings to an implementer agent (use daintree.agents.relay-review-feedback), to REVIEW the change rather than ready it (use daintree.review.review-change), or to fix a failing check (use daintree.ci.diagnose-and-fix).

## daintree.workflow.start-work-on-issue
title: Start work on a forge issue
summary: How to pick a forge issue and start work on it through workflow.startWorkOnIssue, which spawns the agent and auto-attaches a BACKGROUND supervisor watcher.
whenToUse: Use when the user asks to start work on ONE forge issue they have already settled on — pick up a ticket, begin an issue, set up a worktree/branch for it and put an agent on it. Do not use when the issue is NOT yet chosen and the job is searching or triaging the backlog for a candidate (use daintree.workflow.find-issue-work); for SEVERAL issues at once, an agent per ticket, or working a batch in parallel (use daintree.orchestration.fan-out-work); to finish work and open a PR (use daintree.workflow.prep-branch-for-review); to check CI, a review decision or the issue thread on work already underway (use daintree.workflow.follow-up-on-issue); for a change with no forge issue behind it (use daintree.edits.spawn-visible-agent); to create a worktree from a workspace recipe rather than an issue (use daintree.recipe.run-or-create); or to pick up / resume work already in flight from an earlier session (use daintree.orchestration.status-and-resume).

## daintree.worktree.create-plain-worktree
title: Create a plain Daintree worktree
summary: Create a standalone Daintree worktree for a new or existing branch through the typed worktree wrapper, without launching a recipe or agent.
whenToUse: Use when the user asks to create, add, or set up a plain worktree for a new branch or an existing branch — "create a worktree", "make a new branch in its own worktree", or "check out this branch as a worktree" — and they do not want a recipe or agent launched. Do not use for a worktree with a workspace recipe (use daintree.recipe.run-or-create), for starting a forge issue with an agent (use daintree.workflow.start-work-on-issue), for spawning an agent into an existing worktree (use daintree.edits.spawn-visible-agent), or for deleting a worktree (use daintree.orchestration.workspace-cleanup).

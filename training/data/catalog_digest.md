# Daintree runbook catalog — routing digest

## daintree.agents.answer-waiting-agent
title: Answer a waiting agent
summary: Answer a waiting agent’s prompt — one agent, or a whole cohort asking at once — with the exact protocol reply, wait for them to continue, and report the requested results.
whenToUse: Use when one or more already-running visible agents/terminals are waiting on a QUESTION and the user wants them answered — "the agent is asking something, tell it yes", "it's blocked on a prompt", "three of them are waiting on questions, unblock them", "answer the waiting agents and report the result". Also covers an agent blocked on a permission or trust dialog rather than a typed question — waitingReason "approval" ("it wants me to approve something", "it's asking whether to trust the folder") — which needs the same move of reading what it wants and sending the answer. Includes the fan-out case where several ask at once (a wait or status read shows several at waitingReason "question" or "approval"). Do not use when the agent is asking nothing but is hung, silent, or behind a bad terminal id (daintree.agents.recover-agent), to change the course of a working agent that asked nothing (daintree.agents.steer-running-agent), to put the user's own question to an agent that already exists (daintree.agents.ask-running-agent), for a whole-fleet sweep where answering is only one of several actions (daintree.orchestration.supervise-fleet), to spawn a new agent to ask a question (daintree.agents.ask-and-relay or daintree.edits.spawn-visible-agent), or to poll agents for opinions, votes, or verdicts (daintree.agents.poll-pinned-agents).

## daintree.agents.ask-and-relay
title: Ask an agent and relay its answer
summary: Launch one configured agent read-only, ask it one question, collect its answer when it finishes, and report it with attribution.
whenToUse: Use when the user wants ONE agent asked ONE question and its answer brought back — "ask claude what it makes of the retry logic", "get an agent to look at the auth module and tell me what it finds", "spawn something to check X and report back", "ask Codex what the risks are". The signal is ONE agent and that the DELIVERABLE IS THE ANSWER — read-only, one launched agent, its reply collected when it finishes and relayed with attribution. Do not use when the deliverable is WORK rather than an answer — implementing, refactoring, fixing (use daintree.edits.spawn-visible-agent); when the user asks about the code itself — "where is X", "how does the auth flow work" — and not for a particular agent's view (daintree.explore.repository, which delegates the reading itself); when the plan it would write is to be approved and then built (daintree.orchestration.plan-then-implement); for the same question put to several agents, or a poll of the pinned or configured fleet (daintree.agents.poll-pinned-agents); for multi-round debate, a scored competition or a judged interview (the relevant daintree.orchestration runbook); or when the agent already exists — put the question to it with daintree.agents.ask-running-agent, answer its own question with daintree.agents.answer-waiting-agent, or use daintree.agents.recover-agent if it has gone wrong.

## daintree.agents.ask-running-agent
title: Ask an existing agent a question
summary: Get an answer from an agent that is already open because it holds the context — read it from what the agent already said when it is there, otherwise ask once at its prompt without derailing its task — and relay it with attribution.
whenToUse: Use when the user wants an answer FROM an agent that already exists, because that agent holds the context: "ask the Claude doing the auth refactor why it chose JWT", "what did the codex agent decide about the schema?", "what did it say last?", "ask terminal 4 whether it ran the tests", "ask the implementer what is left to do". The deliverable is that agent's own answer, quoted with attribution, with its task left running. Do not use to launch a NEW agent to answer a question (daintree.agents.ask-and-relay), to answer a question the agent is asking you (daintree.agents.answer-waiting-agent), to change what it is doing (daintree.agents.steer-running-agent), to poll freshly launched agents on one question (daintree.agents.poll-pinned-agents), for a state sweep of the whole fleet (daintree.orchestration.supervise-fleet), or to check whether its claimed work is actually true (daintree.orchestration.verify-agent-work).

## daintree.agents.check-usage-limits
title: Check how much usage an agent has left
summary: Read an agent CLI's own account-usage view — remaining session, five-hour and weekly allowance, premium requests or credits, and when each resets — with the command that only reads, and report what is left and where each figure came from.
whenToUse: Use when the user wants to know how much of an AI agent CLI's plan allowance is LEFT — usage limits, rate limits, quota, premium requests, credits, how close they are to a weekly or five-hour cap, when an agent's usage resets, or how to check usage in a given agent CLI — for Claude Code, Codex, Grok, Antigravity, Gemini, Copilot, Kimi or any other configured agent, one agent or several, and for a follow-up asking the same about another agent. The deliverable is the account figures read off the agent's own usage screen, never an answer the agent composes, so the work is running a read-only command inside the agent rather than giving it a task. Do not use for the allowance on other machines a hub reaches through their assistants (daintree.hosts.check-usage-limits), to put a question about code or the project to an agent (daintree.agents.ask-and-relay), to start agents on work in parallel (daintree.orchestration.fan-out-work), to be told later when something finishes (daintree.orchestration.watch-outcome), for Daintree's own sign-in or health (daintree.diagnostics), to move a task off an agent that has hit its limit (daintree.agents.hand-off-task), to say which issues or tasks are still left to do (daintree.workflow.find-issue-work), to choose which model or reasoning effort an agent launches with, even to save budget (daintree.edits.spawn-visible-agent), or to run any other of the agent's own slash commands (daintree.agents.run-agent-command).

## daintree.agents.hand-off-task
title: Hand a task over to another agent
summary: Move an unfinished task from one agent to a different agent or a fresh session in the same checkout — stop the first, build a handoff from git and its own words (done, uncommitted, decided, tried and failed, next), and brief the successor to continue rather than restart.
whenToUse: Use when a task an agent has STARTED must be finished by a DIFFERENT agent or a fresh session, in the same checkout: "Claude hit its usage limit, have Codex finish it", "its context window is used up, start a fresh session that carries on where it left off", "it is going in circles, give it to Claude", "swap it for Gemini and keep going", "take over from that agent and finish it yourself". The deliverable is the successor working in the same worktree from a handoff brief checked against git, with the predecessor stopped and left open. Do not use to correct an agent that keeps the task (daintree.agents.steer-running-agent), to reopen the SAME closed session (daintree.orchestration.status-and-resume), to move the same agent to another worktree (daintree.worktree.relocate-agents), to rescue a hung or failed spawn (daintree.agents.recover-agent), to read how much usage is left (daintree.agents.check-usage-limits), to send review findings to a fixer (daintree.agents.relay-review-feedback), to start new work from scratch (daintree.edits.spawn-visible-agent), to give a task to the assistant on another machine (daintree.hosts.delegate-to-host) or move one a host started (daintree.hosts.reassign-host-work), to compact or clear the same agent's context (daintree.agents.run-agent-command), to re-plan several agents around urgent work (daintree.orchestration.reprioritize-work), to replace the coordinator of a multi-agent run (daintree.orchestration.hand-off-orchestration), or to carry only the useful part of a failed attempt into a new branch (daintree.orchestration.salvage-failed-attempt).

## daintree.agents.poll-pinned-agents
title: Poll pinned agents
summary: Put the same question to several agents (named ones, the pinned or the configured fleet) independently, collect each answer from its notice, and report every answer, the vote tally or a consensus.
whenToUse: Use when the user wants the SAME question put to several agents and each independent answer brought back: "ask Claude, Codex and Gemini what they think of this", "get three agents to answer this and show me their answers", "have the pinned agents vote on my three options and tally it", or a poll of the pinned or configured agent fleet for opinions, votes or rankings among options, verdicts or recommendations with a consensus. The deliverable is their answers, not work, and the agents never see each other. Do not use when each agent is instead to be given its own unit of real work (use daintree.orchestration.fan-out-work), to build a prototype of a different option (use daintree.orchestration.spike-options) or to test a different suspected cause (use daintree.orchestration.hypothesis-split); for a single new agent (use daintree.agents.ask-and-relay) or one question to one agent that already exists (use daintree.agents.ask-running-agent); for multi-round debate or collaboration (use daintree.orchestration.multi-agent), for an open-ended dialogue where the agents talk to each other (use daintree.orchestration.conversation), for a judged competition over the agents' own submissions or an interview (use daintree.orchestration.competition or daintree.orchestration.interview), or for breaking a tie (use daintree.orchestration.runoff-tiebreaker).

## daintree.agents.postmortem-run
title: Post-mortem a failed agent run
summary: Work out why a finished agent run went wrong — find the first point it diverged from its brief using its transcript, diff and Daintree's record, classify the cause, sort salvageable work, and propose concrete prevention without replaying the run.
whenToUse: Use when an agent run is OVER and the user wants to know WHY it went wrong and how to stop it happening again — "why did that agent go off the rails?", "what went wrong with last night's Codex run?", "post-mortem this failed attempt", "why did it rewrite half the repo when I asked for one fix?", "learn from this so it doesn't happen again". The deliverable is the first point of divergence with evidence, a classified cause (brief, environment, agent or orchestration), what of the work is salvageable, and prevention proposed with exact text, applied only on request. Do not use to rescue an agent that is stuck or broken now (use daintree.agents.recover-agent), to change the course of one still working (use daintree.agents.steer-running-agent), to check whether a finished agent's claim is true (use daintree.orchestration.verify-agent-work), to reconstruct what is still in flight (use daintree.orchestration.status-and-resume), for a production incident (use daintree.debug.investigate-outage), when Daintree itself is misbehaving (use daintree.diagnostics), only to save a rule to memory (use daintree.memory.manage-project-memory), to reverse what the run changed (use daintree.git.undo-agent-changes), to move its salvageable part onto a fresh branch (use daintree.orchestration.salvage-failed-attempt), or for a run across the Remote Hosts (use daintree.hosts.postmortem-swarm).

## daintree.agents.recover-agent
title: Recover a broken agent or spawn
summary: Triage an agent that went wrong — reconcile the launch from what Daintree lists, tell a hang from a bad id, and re-arm observation of an unwatched agent instead of restarting it.
whenToUse: Use when something has gone WRONG with an agent or its spawn — "my agent is stuck", "it has been sitting there for ages", "did that agent even start?", "the spawn failed", "nothing happened when you launched it", "that terminal id does not work", "this agent has no watcher on it", "there is an agent running from earlier that nobody is watching", "is it hung or just slow?", "my agents were cut off when the laptop slept, get them going again". Covers a launch that returned no terminalId or an ambiguous result, a hung or unresponsive agent, a turn cut off by an error (the machine slept, the network dropped) that must be told to continue, a stale or mistyped terminal id, and adopting an orphaned or unsupervised agent. Do not use when the agent is healthy and merely ASKING something — answer it with daintree.agents.answer-waiting-agent; for routine triage of a fleet where nothing is broken use daintree.orchestration.supervise-fleet or daintree.orchestration.status-and-resume; to start fresh work use daintree.edits.spawn-visible-agent; to redirect or stop a healthy agent the user wants on another course use daintree.agents.steer-running-agent; to have a different agent continue its task use daintree.agents.hand-off-task; when the run is over and the user asks why it went wrong use daintree.agents.postmortem-run; when agents are slow because the machine itself is overloaded use daintree.runtime.relieve-resource-contention. Do NOT use when the agent and its launch are both healthy and the user is questioning something YOU did — "why did you not wait", "why did you spawn that" — a complaint about your own handling is not a broken agent, so answer it directly rather than opening a recovery; for a task delegated to another machine's assistant that never came back use daintree.hosts.recover-and-clean-up.

## daintree.agents.relay-review-feedback
title: Relay review feedback to an implementer
summary: Get one agent's review findings to another agent that fixes them, reading an existing reviewer's output or launching the reviewer the user named, with calibration and the fixer's reply when asked.
whenToUse: Use when review findings from one AGENT must reach another agent that fixes them: read an existing reviewer agent's output, review or notes and point/send an existing implementer agent to it, or launch the reviewer the user names ("have Codex review this file without changing anything, then pass its findings to Claude and have Claude fix them") and relay its findings to the named fixer; optionally telling the target how to weigh the source or to report what it changed. Do not use for feedback that lives on the forge: PR review threads to fix (use daintree.forge.address-pr-review), or a review decision, failing check or issue thread to fetch and pass on (use daintree.workflow.follow-up-on-issue). Nor to judge whether the reviewed work is actually done or correct (use daintree.orchestration.verify-agent-work), when you review the change yourself and no agent is named to fix it (use daintree.review.review-change), for a correction in the user's own words to a working agent (use daintree.agents.steer-running-agent), when review and fixes repeat until the reviewer approves (use daintree.orchestration.review-until-approved), for a cohort of agents reviewing each other in rotation (use daintree.review.cross-review-cohort), to spawn a new single agent and ask it a question with no fixer (use daintree.agents.ask-and-relay), to poll several agents for independent opinions (use daintree.agents.poll-pinned-agents), or to run multi-round collaboration among agents (use daintree.orchestration.multi-agent).

## daintree.agents.run-agent-command
title: Run a CLI command in an open agent
summary: Drive an agent that is already open with one of its own slash commands — compact, clear or new, model switch, review, a project command — chosen from Daintree's command listing, typed at its idle prompt, menus answered by label, and the effect read back from its screen.
whenToUse: Use when an agent that is already open should run one of its OWN CLI slash commands rather than be given a task: "compact Claude's context, focusing on the auth work", "/clear that agent's context and brief it fresh on X", "switch the Codex pane to another model", "run /review in the codex terminal", "run our /deploy-check command in that agent", "what slash commands does Codex have here?". The deliverable is the command's visible effect read back from that agent's screen, or the list of commands it offers. Do not use for usage, quota or rate-limit figures (daintree.agents.check-usage-limits), for a command that is a NEW agent's first turn (daintree.edits.spawn-visible-agent) or a per-issue command chain (daintree.orchestration.fan-out-work), for a plugin-contributed skill (daintree.skills.use-plugin-skill), for a correction in plain words (daintree.agents.steer-running-agent), or for moving the task to a fresh agent (daintree.agents.hand-off-task).

## daintree.agents.steer-running-agent
title: Steer or stop a running agent
summary: Change the course of an agent that is already working — stop its turn when the change cannot wait, confirm the stop from its screen, send one correction that keeps the rest of its task, and check that it took the new course.
whenToUse: Use when an agent that is ALREADY WORKING on a task, or paused mid-task at its prompt, must change course or stop: corrected, redirected, given an extra requirement, or told to stop what it is doing — "tell Claude to stop touching the migrations", "it's going the wrong way, make it use the existing helper", "interrupt Codex and tell it to use pnpm", "also make it keep the old API working", "stop that agent's turn but keep it open", or one correction sent to several running agents. The deliverable is each agent stopped, or working on the corrected course, confirmed from its own screen and reply. Do not use when the agent is ASKING a question or waiting on an approval (daintree.agents.answer-waiting-agent), is hung, silent or its launch is unclear (daintree.agents.recover-agent), to forward a reviewer's findings (daintree.agents.relay-review-feedback), to ask it something without changing its work (daintree.agents.ask-running-agent), to give the task to a different agent (daintree.agents.hand-off-task), to run one of its CLI commands such as /compact (daintree.agents.run-agent-command), to bring agents to a resumable stop for the day (daintree.orchestration.park-work), to close panels (daintree.orchestration.workspace-cleanup), to move it to another worktree (daintree.worktree.relocate-agents), to re-plan several agents around newly urgent work (daintree.orchestration.reprioritize-work), to settle which of two agents duplicating one task keeps it (daintree.orchestration.resolve-task-collisions), to take back changes it already made (daintree.git.undo-agent-changes), or on a Remote Host's lane steering work the hub delegated there (daintree.hosts.steer-for-hub).

## daintree.ci.diagnose-and-fix
title: Diagnose and fix a failing check
summary: Take a red test, build or PR check from symptom to verified green — evidence first, fix second, independent verification last.
whenToUse: Use when something is FAILING and the user wants it working — "the tests are failing", "why is CI red", "the build broke", "this check won't pass", "fix the failing test" — including the fix-and-verify loop that follows. Do not use to judge a change that already passes (use daintree.review.review-change), to confirm an agent did what it claimed (use daintree.orchestration.verify-agent-work), to read a PR's review state or comment on its issue without a failure to fix (use daintree.workflow.follow-up-on-issue), to fix or answer a reviewer's comments on a PR (use daintree.forge.address-pr-review), to ready a branch for review (use daintree.workflow.prep-branch-for-review), or when Daintree itself, not the project, is misbehaving (use daintree.diagnostics). Nor for a test that fails only sometimes and needs its rate or cause found (use daintree.ci.hunt-flaky-test), a reported bug with nothing red yet that first needs a failing test (use daintree.debug.reproduce-bug), finding the commit that broke it (use daintree.git.bisect-regression), only running the checks and reporting (use daintree.ci.run-local-checks), merge or rebase conflicts with the base (use daintree.git.sync-with-base), branches that each pass alone but break once combined (use daintree.git.resolve-semantic-conflict), a production outage or live incident (use daintree.debug.investigate-outage), a version bump and the breakage it causes (use daintree.deps.upgrade-dependency), one agent per rival cause of a bug with no failing check (use daintree.orchestration.hypothesis-split), or failing tests written first for another agent to implement against (use daintree.orchestration.test-first-split).

## daintree.ci.hunt-flaky-test
title: Hunt down and stabilise a flaky test
summary: Measure a suspected flaky test's failure rate under controlled variation, isolate the trigger and root cause (race, shared state, polluting neighbour, time, randomness), and when asked fix the source and prove it with a consecutive-pass gate.
whenToUse: Use when a test passes SOMETIMES and fails other times, and the user wants that measured, explained or stabilised: "this test is flaky", "fails about one run in ten", "passes locally but randomly fails in CI", "run it 50 times and see", "which test is polluting this one?", "stabilise the reconnect test without sleeps or retries". The deliverable is a failure rate per condition, the trigger and root cause with evidence, and, when a fix is asked for, a source fix proven by consecutive passes. Do not use for a test that fails EVERY time (use daintree.ci.diagnose-and-fix); to turn a bug report into a first failing test (use daintree.debug.reproduce-bug); or just to run the suite and report pass or fail (use daintree.ci.run-local-checks).

## daintree.ci.run-e2e-suite
title: Run end-to-end tests against a worktree's own app
summary: Run a browser or API end-to-end suite for one worktree, here or on a Remote Host, proving the server it hits is that checkout's at that revision, collect failures and artifact references, and stop only what you started.
whenToUse: Use when the user wants END-TO-END, BROWSER or INTEGRATION tests run that need the app (and maybe its database) up, and the green result tied to the right server: "run the Playwright tests in this worktree", "run e2e against my branch", "run the Cypress suite headless", "run the integration tests that need the server running", "run the browser tests against the remote worktree's own app", "check the host-side integration tests did not hit another checkout's server", "verify the e2e server provenance and keep readable trace references". The deliverable is the e2e result for THAT worktree's code: where the runner, browser and server ran, the base URL used (a host's localhost is not a Shell's forwarded URL), the server's directory and build revision against the exact HEAD, pass and fail counts, each failure with report and trace references naming host, worktree and revision, and what was started and stopped; a wrong or stale server is rejected, never green. Do not use for unit, lint, typecheck or build runs that need no running app (use daintree.ci.run-local-checks); to make a failing e2e test pass (use daintree.ci.diagnose-and-fix); to give worktrees their own persistent ports or database (use daintree.worktree.provision-local-environment); to debug a page interactively in a dev preview (use daintree.runtime.debug-web-app); only to start a dev server and leave it running (use daintree.terminals.run-visible-command); one commit under several environments across hosts (use daintree.hosts.run-validation-matrix); or one suite split between hosts (use daintree.hosts.shard-test-suite).

## daintree.ci.run-local-checks
title: Run the project's checks locally
summary: Find the project's real test, lint, typecheck and build commands, run them in the exact worktree (or across several agents' worktrees), and report a pass, fail or incomplete result per worktree bound to the revision tested, fixing nothing.
whenToUse: Use when the user wants the project's checks RUN and the results reported, with nothing known to be broken yet: "run the tests", "run lint and typecheck in the auth worktree", "does it still build?", "run the checks before I push", "run the test suite in every agent's worktree and tell me which are green", "what checks does this project even have?". The deliverable is a result per worktree and check (revision tested, command, passed / failed with the failing lines / incomplete), not a fix. Do not use when a check is already failing and the user wants it working (use daintree.ci.diagnose-and-fix); to decide whether one agent's "done, tests pass" is true (use daintree.orchestration.verify-agent-work); to ready a branch and open a PR (use daintree.workflow.prep-branch-for-review); for end-to-end or browser tests that need the app running (use daintree.ci.run-e2e-suite); to run a command in a terminal the user can watch (use daintree.terminals.run-visible-command); to read a PR's CI on the forge (use daintree.workflow.follow-up-on-issue); to run them at a later time (use daintree.orchestration.watch-outcome); for a ship or no-ship verdict on a release candidate (use daintree.release.assess-readiness); or to try the built installer, image or packed package in a clean setting (use daintree.release.test-distributable).

## daintree.context.curate-copytree-bundle
title: Curate a CopyTree context bundle
summary: Explore the worktree with read-only file tools, settle an explicit list of files and patterns, and generate one bounded CopyTree reference file — copying it to the clipboard only when explicitly asked.
whenToUse: Use when the user asks for a curated CopyTree bundle, context bundle, reference file, or clipboard-ready code context for a feature area, subsystem, bug, review, or later handoff — "bundle everything relevant to X, including supporting files and tests". The deliverable is the FILE itself, deliberately selected: explore first, settle an explicit selection, then one generate call. End on copyTree.generate when only the file is wanted; use copyTree.generateAndCopyFile only when the user explicitly asked for the clipboard. Do not use when context is merely an input to launching or feeding an agent — select the workflow that owns the agent instead (daintree.workflow.start-work-on-issue for one issue, daintree.edits.spawn-visible-agent for one new agent, daintree.context.feed-running-agent for an agent that is already open, or daintree.orchestration.fan-out-work for injecting context across parallel agents). Nor when a bundle has already carried a key or token out (use daintree.security.respond-to-secret-exposure).

## daintree.context.feed-running-agent
title: Give a running agent codebase context
summary: Get a chosen slice of the codebase into an agent that is already open — by pointing it at the files, by a curated CopyTree bundle it reads, or by Daintree's whole-worktree injection only when asked and only after checking which worktree it would inject.
whenToUse: Use when an agent that ALREADY EXISTS should be given codebase context: "inject the context into that Claude", "give the Codex agent the whole auth module as context", "load the spec and the related code into the implementer", "paste the worktree context into terminal 3", "feed it the relevant files before it continues". The deliverable is that agent holding the named context, confirmed from its reply or screen, followed by the user's instruction if they gave one. Do not use to produce a bundle FILE for the user or the clipboard (daintree.context.curate-copytree-bundle), when the context is part of launching a NEW agent (daintree.edits.spawn-visible-agent, daintree.orchestration.fan-out-work for several, daintree.workflow.start-work-on-issue for an issue), to correct what the agent is doing (daintree.agents.steer-running-agent), or to hand its task to a different agent (daintree.agents.hand-off-task).

## daintree.debug.investigate-outage
title: Investigate a production incident with read-only agents
summary: Production is broken now — pin the code to the deployed revision, fan out read-only investigators on the deploy diff, the logs and the failing code path, correlate a timeline and ranked suspects, and hand the user mitigation options without executing any.
whenToUse: Use when PRODUCTION or another deployed environment is broken right now — an outage or live incident, errors or 500s since a deploy — and the user wants it investigated fast: "prod is down", "prod is on fire, get some agents on it", "errors spiked after the deploy", "get agents looking at the logs, the recent deploys and the diff", "what changed that broke checkout?", "help me triage this incident". The deliverable is a timeline, suspects ranked with evidence (commit or PR, log lines, code path) and mitigation options with their blast radius for the user to choose and run; no agent deploys, rolls back, restarts or changes config. Do not use for a failing test or CI check (use daintree.ci.diagnose-and-fix), a bug in the local dev preview (use daintree.runtime.debug-web-app), reproducing a reported bug that is not a live incident (use daintree.debug.reproduce-bug), finding the commit behind a regression you can reproduce locally (use daintree.git.bisect-regression), Daintree itself misbehaving (use daintree.diagnostics), several agents debating one question to a synthesis (use daintree.orchestration.multi-agent), or carrying out a rollback the user has already chosen (use daintree.release.rollback-deployment).

## daintree.debug.reproduce-bug
title: Reproduce a reported bug before fixing it
summary: Turn a bug report or issue into a minimal reproduction, a test or script observed failing for the reported reason on a known revision, or an evidenced could-not-reproduce, fixing nothing.
whenToUse: Use when the user wants a REPORTED bug reproduced rather than fixed: "can you repro #412", "write a failing test for this bug first", "confirm the crash this user reported is real", "does this still happen on main?", "make a minimal repro I can attach to the issue", "have an agent write a reproduction in a scratch worktree". The deliverable is RED EVIDENCE: a test or script plus its exact command, observed failing with the reported symptom on a named revision, or a could-not-reproduce listing every condition tried. Do not use when a test or CI check is already failing and the user wants it green (use daintree.ci.diagnose-and-fix); to find which commit introduced it (use daintree.git.bisect-regression); for a test that passes only sometimes (use daintree.ci.hunt-flaky-test); to put an agent on implementing the issue (use daintree.workflow.start-work-on-issue); for a runtime error in an open dev preview (use daintree.runtime.debug-web-app); to explain code when there is no symptom to reproduce (use daintree.explore.repository); or for a live production incident (use daintree.debug.investigate-outage).

## daintree.deps.upgrade-dependency
title: Upgrade a dependency or framework with verification
summary: Upgrade one package, framework, runtime or toolchain in its own worktree — baseline checks first, the upstream migration guide and codemods applied as their own commit, a constrained fix loop, and a before/after check comparison that separates what the upgrade broke from what was already red.

# Daintree runbook catalog — routing digest

## daintree.agents.answer-waiting-agent
title: Answer a waiting agent
summary: Answer a waiting agent’s prompt — one agent, or a whole cohort asking at once — with the exact protocol reply, wait for them to continue, and report the requested results.
whenToUse: Use when one or more already-running visible agents/terminals are waiting on a QUESTION and the user wants them answered — "the agent is asking something, tell it yes", "it's blocked on a prompt", "three of them are waiting on questions, unblock them", "answer the waiting agents and report the result". Also covers an agent blocked on a permission or trust dialog rather than a typed question — waitingReason "approval" ("it wants me to approve something", "it's asking whether to trust the folder") — which needs the same move of reading what it wants and sending the answer. Includes the fan-out case where several ask at once (a wait or status read shows several at waitingReason "question" or "approval"). Do not use when the agent is asking nothing but is hung, silent, or behind a bad terminal id (daintree.agents.recover-agent), for a whole-fleet sweep where answering is only one of several actions (daintree.orchestration.supervise-fleet), to spawn a new agent to ask a question (daintree.agents.ask-and-relay or daintree.edits.spawn-visible-agent), or to poll agents for opinions, votes, or verdicts (daintree.agents.poll-pinned-agents).

## daintree.agents.ask-and-relay
title: Ask an agent and relay its answer
summary: Launch one configured agent read-only, ask it one question, collect its answer when it finishes, and report it with attribution.
whenToUse: Use when the user wants ONE agent asked ONE question and its answer brought back — "ask claude what it makes of the retry logic", "get an agent to look at the auth module and tell me what it finds", "spawn something to check X and report back", "ask Codex what the risks are". The signal is ONE agent and that the DELIVERABLE IS THE ANSWER — read-only, one launched agent, its reply collected when it finishes and relayed with attribution. Do not use when the deliverable is WORK rather than an answer — implementing, refactoring, fixing, or an investigation the user wants to watch and steer (use daintree.edits.spawn-visible-agent); for the same question put to several agents, or a poll of the pinned or configured fleet (daintree.agents.poll-pinned-agents); for multi-round debate, a scored competition or a judged interview (the relevant daintree.orchestration runbook); or when the agent already exists — answer it with daintree.agents.answer-waiting-agent, or use daintree.agents.recover-agent if it has gone wrong.

## daintree.agents.check-usage-limits
title: Check how much usage an agent has left
summary: Read an agent CLI's own account-usage view — remaining session, five-hour and weekly allowance, premium requests or credits, and when each resets — with the command that only reads, and report what is left and where each figure came from.
whenToUse: Use when the user wants to know how much of an AI agent CLI's plan allowance is LEFT — usage limits, rate limits, quota, premium requests, credits, how close they are to a weekly or five-hour cap, when an agent's usage resets, or how to check usage in a given agent CLI — for Claude Code, Codex, Grok, Antigravity, Gemini, Copilot, Kimi or any other configured agent, one agent or several, and for a follow-up asking the same about another agent. The deliverable is the account figures read off the agent's own usage screen, never an answer the agent composes, so the work is running a read-only command inside the agent rather than giving it a task. Do not use to put a question about code or the project to an agent (daintree.agents.ask-and-relay), to start agents on work in parallel (daintree.orchestration.fan-out-work), to be told later when something finishes (daintree.orchestration.watch-outcome), or for Daintree's own sign-in or health (daintree.diagnostics).

## daintree.agents.poll-pinned-agents
title: Poll pinned agents
summary: Put the same question to several agents (named ones, the pinned or the configured fleet) independently, collect each answer from its notice, and report every answer, the vote tally or a consensus.
whenToUse: Use when the user wants the SAME question put to several agents and each independent answer brought back: "ask Claude, Codex and Gemini what they think of this", "get three agents to answer this and show me their answers", "have the pinned agents vote on my three options and tally it", or a poll of the pinned or configured agent fleet for opinions, votes or rankings among options, verdicts or recommendations with a consensus. The deliverable is their answers, not work, and the agents never see each other. Do not use when each agent is instead to be given its own unit of real work (use daintree.orchestration.fan-out-work), for a single agent (use daintree.agents.ask-and-relay), for multi-round debate or collaboration (use daintree.orchestration.multi-agent), for an open-ended dialogue where the agents talk to each other (use daintree.orchestration.conversation), for a judged competition over the agents' own submissions or an interview (use daintree.orchestration.competition or daintree.orchestration.interview), or for breaking a tie (use daintree.orchestration.runoff-tiebreaker).

## daintree.agents.recover-agent
title: Recover a broken agent or spawn
summary: Triage an agent that went wrong — reconcile the launch from what Daintree lists, tell a hang from a bad id, and re-arm observation of an unwatched agent instead of restarting it.
whenToUse: Use when something has gone WRONG with an agent or its spawn — "my agent is stuck", "it has been sitting there for ages", "did that agent even start?", "the spawn failed", "nothing happened when you launched it", "that terminal id does not work", "this agent has no watcher on it", "there is an agent running from earlier that nobody is watching", "is it hung or just slow?". Covers a launch that returned no terminalId or an ambiguous result, a hung or unresponsive agent, a stale or mistyped terminal id, and adopting an orphaned or unsupervised agent. Do not use when the agent is healthy and merely ASKING something — answer it with daintree.agents.answer-waiting-agent; for routine triage of a fleet where nothing is broken use daintree.orchestration.supervise-fleet or daintree.orchestration.status-and-resume; to start fresh work use daintree.edits.spawn-visible-agent. Do NOT use when the agent and its launch are both healthy and the user is questioning something YOU did — "why did you not wait", "why did you spawn that" — a complaint about your own handling is not a broken agent, so answer it directly rather than opening a recovery.

## daintree.agents.relay-review-feedback
title: Relay review feedback to an implementer
summary: Get one agent's review findings to another agent that fixes them, reading an existing reviewer's output or launching the reviewer the user named, with calibration and the fixer's reply when asked.
whenToUse: Use when review findings from one AGENT must reach another agent that fixes them: read an existing reviewer agent's output, review or notes and point/send an existing implementer agent to it, or launch the reviewer the user names ("have Codex review this file without changing anything, then pass its findings to Claude and have Claude fix them") and relay its findings to the named fixer; optionally telling the target how to weigh the source or to report what it changed. Feedback that must first be fetched from the forge (a PR's review decision, a failing check, an issue thread) is a different job (use daintree.workflow.follow-up-on-issue). Do not use to judge whether the reviewed work is actually done or correct (use daintree.orchestration.verify-agent-work), when you review the change yourself and no agent is named to fix it (use daintree.review.review-change), to spawn a new single agent and ask it a question with no fixer (use daintree.agents.ask-and-relay), to poll several agents for independent opinions (use daintree.agents.poll-pinned-agents), or to run multi-round collaboration among agents (use daintree.orchestration.multi-agent).

## daintree.ci.diagnose-and-fix
title: Diagnose and fix a failing check
summary: Take a red test, build or PR check from symptom to verified green — evidence first, fix second, independent verification last.
whenToUse: Use when something is FAILING and the user wants it working — "the tests are failing", "why is CI red", "the build broke", "this check won't pass", "fix the failing test", "is this flaky?" — including the fix-and-verify loop that follows. Do not use to judge the quality of a change that already passes (use daintree.review.review-change), to confirm an agent did what it claimed (use daintree.orchestration.verify-agent-work), to read a PR's review state or comment on its issue without a failure to fix (use daintree.workflow.follow-up-on-issue), to ready a branch for review (use daintree.workflow.prep-branch-for-review), or when the "failure" is Daintree itself misbehaving rather than the project (use daintree.diagnostics).

## daintree.context.curate-copytree-bundle
title: Curate a CopyTree context bundle
summary: Explore the worktree with read-only file tools, settle an explicit list of files and patterns, and generate one bounded CopyTree reference file — copying it to the clipboard only when explicitly asked.
whenToUse: Use when the user asks for a curated CopyTree bundle, context bundle, reference file, or clipboard-ready code context for a feature area, subsystem, bug, review, or later handoff — "bundle everything relevant to X, including supporting files and tests". The deliverable is the FILE itself, deliberately selected: explore first, settle an explicit selection, then one generate call. End on copyTree.generate when only the file is wanted; use copyTree.generateAndCopyFile only when the user explicitly asked for the clipboard. Do not use when context is merely an input to launching or feeding an agent — select the workflow that owns the agent instead (daintree.workflow.start-work-on-issue for one issue, daintree.edits.spawn-visible-agent for one new agent, or daintree.orchestration.fan-out-work for injecting context across parallel agents).

## daintree.diagnostics
title: Diagnose a broken or misbehaving Daintree
summary: Diagnose Daintree itself from its MCP status, offered tools, workspace snapshot, recent error log and notification history, then give the concrete recovery step.
whenToUse: Use when the question is about DAINTREE'S OWN HEALTH — something is misbehaving ("nothing is responding", "the MCP is disconnected", "I did X and nothing happened", "why can't I…", "why is this tool missing"), the user asks to show recent Daintree errors or notifications, wants diagnostics for a bug report, or wants sign-in confirmed before relying on it. Nothing has to be broken for the sign-in case, because a working Daintree connection says nothing about the agent CLI's own provider sign-in. A plain "is Daintree connected?" with nothing wrong is daintree.foundation. Do not use for a plain how-to, setting or keybinding question; for ordinary project failures; for a specific broken agent/spawn (use daintree.agents.recover-agent); for paused-workflow reconstruction (use daintree.orchestration.status-and-resume); or for red project CI (use daintree.ci.diagnose-and-fix).

## daintree.edits.spawn-visible-agent
title: Spawn a visible agent for edits or exploration
summary: How to handle requests that need a visible agent — to change files or to explore read-only.
whenToUse: Use when the user asks for a direct visible agent to change project files (implement, refactor, fix, add tests, update docs) or to explore/investigate a project read-only, and no more specific workflow applies. Prefer a typed workflow first — daintree.workflow.start-work-on-issue for a forge issue, daintree.workflow.prep-branch-for-review for a PR, daintree.recipe.run-or-create for a workspace recipe, daintree.orchestration.fan-out-work when several independent units each need their own agent, or a poll/competition/interview/multi-agent runbook when several agents work together. This is the fallback SINGLE visible-agent path; if the agent is already running and has gone wrong use daintree.agents.recover-agent, and if an agent that is already running is to be moved to a new or another worktree, with or without a task there, use daintree.worktree.relocate-agents. If all the user wants is ONE read-only question answered and relayed back — the deliverable is the agent's answer, not work landing — use daintree.agents.ask-and-relay instead. If the deliverable is UNDERSTANDING the codebase rather than changing it, use daintree.explore.repository; if it is a judgement on an existing change, use daintree.review.review-change; if it is a failing test or check, use daintree.ci.diagnose-and-fix. Spawn here only when the work begins THIS turn; if it is scheduled to begin at a stated later time, use daintree.orchestration.watch-outcome instead.

## daintree.explore.repository
title: Understand a repository
summary: Answer "what does this repo do" / "where is X" with a read-only investigation and cited evidence.
whenToUse: Use when the user wants to UNDERSTAND the project rather than change it — "what does this repo do", "where is X implemented", "how does the auth flow work", "explain this subsystem", "what would I have to touch to add Y", "find the code that does Z", or orientation before work starts. The deliverable is an explanation with file evidence and nothing on disk changes. Do not use when the user wants files CHANGED (make the change yourself, or use daintree.edits.spawn-visible-agent when they want a visible agent to make it, or daintree.workflow.start-work-on-issue for a forge issue), to judge the quality of a specific change or PR (use daintree.review.review-change), to work out why a check is failing (use daintree.ci.diagnose-and-fix), to ask about DAINTREE itself rather than the project (a documentation question — no runbook needed — or daintree.diagnostics when Daintree is broken), or to pick out files to bundle as context (use daintree.context.curate-copytree-bundle), or when the user names a specific agent to ask and just wants its answer relayed back (use daintree.agents.ask-and-relay).

## daintree.forge.land-pull-request
title: Review-state and land a pull request
summary: Apply public PR lifecycle actions and merge only after an exact-target preview, conclusive required-check evidence, review-state checks and a verified forge result.
whenToUse: Use when the user asks to approve a pull request, request changes or reviewers, mark it ready or draft, dismiss a known review, close or reopen it, or merge, squash or rebase it. Also use for "land this PR", "approve and merge", or "merge it once it is ready". Do not use merely to read PR, CI, review or comment status (use daintree.workflow.follow-up-on-issue), to review code quality and produce findings (use daintree.review.review-change), to fix red CI (use daintree.ci.diagnose-and-fix), to create the PR (use daintree.workflow.prep-branch-for-review), or to watch for a later state transition (use daintree.orchestration.watch-outcome).

## daintree.forge.manage-issue
title: Create and maintain a forge issue
summary: Create, edit, reopen, label or assign an issue against the exact repository, then read it back so public forge state is never inferred from a successful call.
whenToUse: Use when the user asks to file, log or create an issue ("log this as an issue", "log it for later", "turn this bug into an issue"), change an issue title or body, reopen an issue, add or remove labels, or assign or unassign an account, as in "label and assign this ticket". Logging an issue for later is filing it now, not a later wake (not daintree.orchestration.watch-outcome). Do not use to search the backlog for work (use daintree.workflow.find-issue-work), start implementation (use daintree.workflow.start-work-on-issue), read an issue or PR's current status, ask why an issue is still open, or add a closing comment and close it (use daintree.workflow.follow-up-on-issue), or create a pull request (use daintree.workflow.prep-branch-for-review).

## daintree.foundation [FOUNDATION]
title: Daintree orchestration foundation
summary: The base judgment under every Daintree workflow — read state before acting, own terminals deliberately, wait through Daintree notices, prove a finish, judge even-handedly.
whenToUse: Use for a plain what-exists-right-now read of Daintree state — which terminals, agents, worktrees or branches exist — and for a single direct action: reading or focusing ONE terminal, closing ONE the user named, reading whether Daintree is connected when nothing is reported wrong. It is also the DOMAIN FOUNDATION for every daintree.* runbook: co-load it with whatever runbook you pick, and load it ALONE only when no runbook squarely matches. Never load it INSTEAD of one that does: triage of running agents is daintree.orchestration.supervise-fleet, "where were we" across sessions is status-and-resume, tearing several things down is workspace-cleanup, being told later when something finishes is watch-outcome, retitling tabs is daintree.terminals.rename, and anything REPORTED as broken, unresponsive or missing is daintree.diagnostics; spawning, relaying, competitions, interviews, branch prep and issue work all have their own runbook.

## daintree.memory.manage-project-memory
title: Manage project memory
summary: Save, recall, correct, pin and forget durable project facts — without hoarding, duplicating, or storing secrets.
whenToUse: Use when the user asks you to remember something ("remember that we use pnpm", "always run the linter first"), asks what was decided before ("what did we agree about the API shape?", "do you remember why we dropped X?"), wants a saved fact corrected or removed ("forget that", "that's not true any more"), or wants to review, pin or unpin what is stored. Also when you are about to save a fact and should check for an existing one first. Do not use for state that only matters inside this session — a terminal id, a step counter, an in-flight plan (that is a task checkpoint, per daintree.foundation) — for "where were we?" across sessions (use daintree.orchestration.status-and-resume), or to look something up in the project's CODE rather than in memory (use daintree.explore.repository).

## daintree.orchestration.competition
title: Orchestrate a competition or peer-judging among agents
summary: Run a contest among several named agents: each makes one independent entry for the same task (an answer, or its own version of a change in its own worktree), then blind peer votes or the agreed judge compare them and pick the winner or tie.
whenToUse: Use when the user names several agents (or the fleet) and has each produce its OWN independent entry for the SAME task — an interesting fact, a design idea, a quick answer, or its own version of the same code change in its own worktree — and then wants the entries compared and a winner picked: "have Claude and Codex compete", "each writes its own version, then tell me which is better", award points, send each agent the others' submissions to pick the best, tally, declare a winner. The signal is two-stage: rival entries for one task, then a verdict on them. A vote over options YOU supplied, even one scored and tallied, is a fleet poll, not a competition. Do not use when each agent instead gets its own DIFFERENT unit of real work (daintree.orchestration.fan-out-work), for independent reviews whose findings are merged rather than ranked (daintree.review.review-change), a judge-led interview (daintree.orchestration.interview), a poll for opinions with no scoring (daintree.agents.poll-pinned-agents), collaborative debate toward one synthesized answer (daintree.orchestration.multi-agent), a debate that ends by voting a position off (daintree.orchestration.debate-elimination), a runoff after a tie (daintree.orchestration.runoff-tiebreaker), or moving agents that are already running into worktrees (daintree.worktree.relocate-agents).

## daintree.orchestration.conversation
title: Facilitate a live agent conversation
summary: Relay a live back-and-forth conversation among two or more agents, giving each the floor in turn and catching it up on what the others said since it last spoke while you drive the rounds.
whenToUse: Use when the user asks you to facilitate, host, relay, moderate, or keep going a live back-and-forth conversation between TWO OR MORE agents — “get them talking,” “let them talk to each other,” “facilitate a conversation,” “have a group chat/roundtable/panel discussion,” “have the three of them hash it out,” or “see where it goes.” Participant count is just a parameter of this runbook. Do not use for a one-shot question to one agent (use daintree.agents.ask-and-relay), an independent poll with no cross-talk (use daintree.agents.poll-pinned-agents), a judged interview that names a winner (use daintree.orchestration.interview), a scored competition or vote (use daintree.orchestration.competition), a post-tie runoff (use daintree.orchestration.runoff-tiebreaker), a debate that ends by voting a position off (use daintree.orchestration.debate-elimination), or several agents collaborating toward ONE synthesized answer or convergence rather than an open-ended visible dialogue (use daintree.orchestration.multi-agent).

## daintree.orchestration.debate-elimination
title: Run agent debate with elimination vote
summary: Facilitate a multi-agent debate, collect final positions, run a peer vote to eliminate the weakest position, and report the tally.
whenToUse: Use when the user asks several agents to debate a topic and then eliminate, vote off, remove, or identify the weakest agent/position after the debate, including when the elimination request arrives mid-debate. Do not use for a collaborative debate that ends in one synthesized answer with no vote-off (use daintree.orchestration.multi-agent), an open-ended visible conversation among agents with no elimination vote (use daintree.orchestration.conversation), a one-shot independent scored contest or best-entry vote (use daintree.orchestration.competition), a simple fleet poll with no debate (use daintree.agents.poll-pinned-agents), or a runoff after a tied vote (use daintree.orchestration.runoff-tiebreaker).

## daintree.orchestration.execute-durable-workflow
title: Execute a durable workflow graph
summary: Plan and advance dependency-aware work across turns with a caller-owned dependency plan, exact resource links, evidence and resume-time reconciliation.
whenToUse: Use for a substantial multi-step goal with dependent phases that must survive turns, restarts or asynchronous waits — migrations, delegate-then-verify work, several ordered changes, or "track this plan and resume it later". Use when the user explicitly asks for a durable plan, dependencies, progress tracking, reconciliation or a workflow graph. Do not use for a one-step action, independent parallel fan-out (use daintree.orchestration.fan-out-work), a status-only "where were we" sweep (use daintree.orchestration.status-and-resume), simple agent supervision (use daintree.orchestration.supervise-fleet), or a single future notification (use daintree.orchestration.watch-outcome).

## daintree.orchestration.fan-out-work
title: Fan out disjoint work across parallel agents
summary: Launch one agent terminal per independent GitHub issue or task, each in its own worktree. Look up custom commands and skills, run each terminal's commands in order with verification, and supervise the parallel issue chains independently.
whenToUse: Use for a BATCH of independent issues or tasks, one agent terminal per issue or worktree. Includes Codex or Claude custom command/skill sequences — implement each issue, then review it, then prepare its PR — with each terminal advancing independently and a failed issue stopping only its own chain. Also use to split one goal into disjoint file-scoped tasks or open a coding-agent terminal in each existing issue worktree. PLURALITY plus INDEPENDENCE is the signal. Also a ROLLING QUEUE under a cap — "no more than 6 at a time", "start the next one whenever one finishes", "keep going until all 30 are done" — including refilling it as each unit finishes — a list of work plus a concurrency cap is this runbook, not a timer or PR runbook. Exclude one issue (daintree.workflow.start-work-on-issue), one agent (daintree.edits.spawn-visible-agent), agents collaborating on the same deliverable (daintree.orchestration.multi-agent), rival solutions (daintree.orchestration.competition), supervising/resuming a fleet already running (daintree.orchestration.supervise-fleet, daintree.orchestration.status-and-resume), opinions rather than work (daintree.agents.poll-pinned-agents), rescuing one stuck agent (daintree.agents.recover-agent), or separating agents that are ALREADY RUNNING into a worktree each, where the terminals exist and are to be relocated rather than replaced (daintree.worktree.relocate-agents).

## daintree.orchestration.interview
title: Run a judge-led interview competition among agents
summary: One agent interviews several others on a topic while you relay questions and answers — optionally with the judge verifying claims against the codebase and narrowing to a top 2 — until it names a winner.
whenToUse: Use when the user asks to have one agent interview, question, or grill several other agents on a topic and expects a winner — "have one agent interview the others and pick the best", "which of these should be my pair programmer?". Covers both depths, a light Q&A interview and a deep one where the judge verifies candidates' claims against the codebase, issues challenging follow-ups, and narrows to a top 2 before the verdict. Do not use for a plain one-round poll with no interviewer (use daintree.agents.poll-pinned-agents), a scoring-only competition where entries are judged rather than questioned (use daintree.orchestration.competition), or an open-ended dialogue with no judge and no winner (use the daintree.orchestration.conversation runbook).

## daintree.orchestration.multi-agent
title: Orchestrate multiple agents on one problem
summary: Spawn or use explicitly named open agents, relay their work between them with terminal.sendCommandOwned, and synthesize ONE answer — collaborative multi-agent work driven until the cohort converges.
whenToUse: Use when several agents must work ONE problem together and you relay between them until they CONVERGE on a single synthesized answer — debate until they converge, collaborate, cross-check, iterate toward one merged result. The signal is a synthesis target: the deliverable is the ONE answer you assemble, not a dialogue. Do not use when each agent gets its OWN independent unit of work with no shared deliverable (use daintree.orchestration.fan-out-work); for an open-ended visible dialogue — let them talk, see where it goes (use daintree.orchestration.conversation); a debate that ends by voting a position off (use daintree.orchestration.debate-elimination); independent submissions scored or peer-voted to pick a winner (use daintree.orchestration.competition); the same question put to several agents with each answer brought back, or a one-shot independent poll (use daintree.agents.poll-pinned-agents); or forwarding one agent's review to another (use daintree.agents.relay-review-feedback).

## daintree.orchestration.runoff-tiebreaker
title: Run a runoff tie-breaker for an agent competition
summary: Break a tie in an agent voting competition by getting new submissions from tied entrants, polling the original cohort, and tallying the runoff accurately.
whenToUse: Use when an agent competition, poll, or peer-vote ends in a tie and the user asks for a tie-breaking round or runoff using the same cohort. Do not use to start a fresh competition or poll (use daintree.orchestration.competition or daintree.agents.poll-pinned-agents), and do not spawn new agents unless the user explicitly changes the electorate.

## daintree.orchestration.status-and-resume
title: Status sweep, ledger hygiene and session resume
summary: Reconstruct what is in flight across turns and sessions from run checkpoints, live Daintree state and closed-session history — then correct the stale checkpoint entries nothing else will.
whenToUse: Use when the user asks where were we, what was I working on, catch me up, what is still open or in flight, what happened while I was away, or to pick up / resume something from an earlier session. Also for the workflow list or saved run checkpoint itself — why it still shows finished work as active, tidying stale entries, recording a PR onto an entry — and for after-the-fact forensics over Daintree's recent notifications. Do not use for a plain what-exists-now read of terminals, worktrees or queues (daintree.foundation), to triage the agents running this minute (daintree.orchestration.supervise-fleet), to be told later when something finishes (daintree.orchestration.watch-outcome), to verify one agent's output (daintree.orchestration.verify-agent-work), to close terminals or delete worktrees (daintree.orchestration.workspace-cleanup), or to start an issue (daintree.workflow.start-work-on-issue).

## daintree.orchestration.supervise-fleet
title: Supervise a running agent fleet
summary: Triage every agent already running — finished, working, waiting, failed, unsupervised — in one state-only sweep, act on each class, and report what still needs the user.
whenToUse: Use when agents are ALREADY running and the user wants the fleet swept and acted on — "how's everyone doing?", "anything need me?", "is anyone stuck?", "catch me up on the agents". Also for adopting a running-but-unsupervised agent, "show me the next one" navigation, and reporting which terminals are armed for the user's typed input. Do not use for a plain state read with no action (daintree.foundation), for answering agents that are ASKING (daintree.agents.answer-waiting-agent), for rescuing one broken or hung agent (daintree.agents.recover-agent), for handing out new work (daintree.orchestration.fan-out-work), for "where were we" across sessions (daintree.orchestration.status-and-resume), for proving one agent's work landed (daintree.orchestration.verify-agent-work), for watching past this turn (daintree.orchestration.watch-outcome), or for retitling tabs (daintree.terminals.rename).

## daintree.orchestration.verify-agent-work
title: Verify an agent actually did the work
summary: Test an agent's "done" against evidence — cheap git reads, the diff, checks you run yourself, a separate reviewer when it needs real inspection — then route on verified, unverified, or contradicted.
whenToUse: Use when the user wants a finished agent's work checked before it is trusted — "did it actually do it?", "check that the agent did what I asked", "verify this before I merge", "it says the tests pass, confirm that", "I don't trust that result" — or when an agent reports done and the next step is irreversible (commit, push, merge, close, hand off). Also to judge a claim against acceptance criteria, or when the tail seems to contradict what the agent said. Do not use to sweep the whole fleet rather than judge ONE result (daintree.orchestration.supervise-fleet), to ready a branch or open a PR (daintree.workflow.prep-branch-for-review), to forward findings to an implementer (daintree.agents.relay-review-feedback), to wait on an agent still running (daintree.orchestration.watch-outcome), for "where were we" across sessions (daintree.orchestration.status-and-resume), or to JUDGE a change on its merits rather than check a claim about it (daintree.review.review-change).

## daintree.orchestration.watch-outcome
title: Watch an outcome unattended
summary: Arrange to be told when running agent work stops — a Daintree notice on a launch, a send or a running terminal — and say plainly when a timed, conditional or after-shutdown trigger has no real mechanism, without starting the deferred work now.
whenToUse: Use when the user wants something to happen LATER rather than now — either to be woken ("run this overnight and wake me", "let me know when the build finishes", "ping me when the PR merges", "remind me in an hour", "keep an eye on it while I'm out") or to have something DONE unattended at a chosen time ("in ten minutes spawn a terminal and run the tests", "in 10 minutes' time spawn a terminal and run the test suite", "in half an hour send npm test to the build terminal", "wait an hour then start the migration", "at 6pm kick off the deploy check"). Any deferred action belongs here, INCLUDING one that spawns an agent — a delayed spawn is a scheduled action, not an immediate one, so do not fall through to daintree.edits.spawn-visible-agent just because the verb is "spawn" — that runbook is for spawning NOW. Also to stop waiting on a notice you arranged. Do not use for a plain read of whether one terminal is still running right now (daintree.foundation), a one-off check of an agent that already finished (daintree.orchestration.verify-agent-work), triage of what is running now (daintree.orchestration.supervise-fleet), a rolling queue of agent work under a concurrency cap even when it has a periodic check (daintree.orchestration.fan-out-work), what happened while you were away (daintree.orchestration.status-and-resume), or wholesale teardown (daintree.orchestration.workspace-cleanup). A one-off read of CI, checks, reviews or an issue thread is not a watch at all (use daintree.workflow.follow-up-on-issue).

## daintree.orchestration.workspace-cleanup
title: Tear down a workspace safely
summary: The confirmation gate for teardown — inventory, classify safe/unsafe/unknown, get an explicit go-ahead, then retire observation, close terminals, delete worktrees and close the run's checkpoint in dependency order.
whenToUse: Use ONLY when the user explicitly asks to tear down workspace state after a fan-out, competition or long session — "close these", "clean up", "tidy up the terminals", "shut it all down", "disarm everything", "delete that worktree", "mark those workflows done". A cleanup request in the user's own words is required; never select this for a status question, and never treat it as permission to close anything on your own initiative. Do not use for closing ONE named terminal (daintree.foundation covers that), to stop waiting on a notice with nothing else torn down (daintree.orchestration.watch-outcome), to triage or check on a running fleet (daintree.orchestration.supervise-fleet), to answer "what is running" or "where were we" (daintree.orchestration.status-and-resume), or to judge whether an agent's work is good (daintree.orchestration.verify-agent-work).

## daintree.recipe.run-or-create
title: Run a Daintree workspace recipe, or create a worktree with one
summary: List, inspect and run an EXISTING Daintree workspace recipe — or create a worktree with one as its startup recipe — then check which terminals started, including any LIVE agent. Nothing here authors or edits a recipe.
whenToUse: Use when the user asks to list, inspect, load, run or apply an existing Daintree workspace recipe, or to create a worktree with a startup recipe. Also use when they ask to CREATE or edit a recipe — only so you can say plainly that no Daintree action authors one and offer what you can actually do. Do not use to create worktrees for agents that are already running (use daintree.worktree.relocate-agents), to create a worktree for a forge issue, which has its own typed workflow (use daintree.workflow.start-work-on-issue), to launch a single agent with no recipe involved (use daintree.edits.spawn-visible-agent), or to delete a worktree and tear the workspace down (use daintree.orchestration.workspace-cleanup).

## daintree.review.review-change
title: Review a change
summary: Review a diff, branch or PR with independent read-only reviewers, and return de-duplicated findings with file evidence.
whenToUse: Use when the user wants a change JUDGED on its merits — "review this", "code review the branch", "is this PR any good", "check this for security problems", "what would you change about this diff", "look over what the agent wrote", "re-audit the fix with fresh Codex sessions for second-order effects". The deliverable is FINDINGS with severity and file evidence. Do not use to check whether an agent did what it claimed before you trust it (use daintree.orchestration.verify-agent-work — that asks "is the claim true", this asks "is the change good"), to ready a branch or open a PR (use daintree.workflow.prep-branch-for-review), to forward review findings to an implementer, or when the user names a reviewer agent and a different agent to fix what it finds (use daintree.agents.relay-review-feedback), to explain how existing code works (use daintree.explore.repository), or to fix a failing check (use daintree.ci.diagnose-and-fix), or when the user names a specific agent to ask and just wants its answer relayed back (use daintree.agents.ask-and-relay).

## daintree.runtime.debug-web-app
title: Debug an existing Daintree dev preview
summary: Diagnose runtime failures in an already-open dev-preview panel from console evidence, fix the cause, reload or restart deliberately, and verify only new navigation output.
whenToUse: Use when the user asks to debug a web app that is already open in Daintree Dev Preview, inspect browser console errors, fix a runtime rendering failure, reload after a frontend fix, or investigate why an existing preview is broken. Also use when the user asks to start or visually inspect a preview. Do not use for ordinary test/build CI failures without a browser runtime symptom (use daintree.ci.diagnose-and-fix), a deployed-site research question, or general code exploration (use daintree.explore.repository).

## daintree.terminals.rename
title: Rename terminal tabs
summary: Give terminals/agents clear tab titles — read what each is doing, then retitle them directly.
whenToUse: Use whenever the user wants to rename terminals/tabs, retitle agents, or "figure out what each of these terminals is doing and give them a title" — especially when several agents share the same name (e.g. all "Claude") and need to be told apart. The deliverable is new TITLES. Do not use when the user wants a report on what the agents are doing rather than a retitle (use daintree.orchestration.supervise-fleet), a plain list of what terminals exist (use daintree.foundation), or an explanation of HOW renaming works rather than the rename itself (a documentation question; no runbook is needed).

## daintree.workflow.find-issue-work
title: Find forge issue work
summary: Search issues or pull requests with a provider-native query; for new work, screen the hits against work already in flight so the shortlist only contains work nobody has started.
whenToUse: Use when the user wants to FIND issues or pull requests rather than start one — search or filter the tracker, triage the backlog, "what should I pick up next", "anything unassigned", "find me a small bug nobody's on" — or to locate past pull requests by text, "find the closed PRs about X", "which PRs touched Y", "did we ever ship Z" — or to check whether an issue is already being worked before committing to it. The deliverable is a shortlist or one chosen issue, NOT a launched agent. Do not use once the issue is chosen and the user wants it started (use daintree.workflow.start-work-on-issue); to launch a batch of issues in parallel, one agent each (use daintree.orchestration.fan-out-work); to reconstruct what was already running across earlier sessions (use daintree.orchestration.status-and-resume); or to read an existing PR's CI, review state or issue thread (use daintree.workflow.follow-up-on-issue).

## daintree.workflow.follow-up-on-issue
title: Follow up on a forge issue
summary: Read where an issue actually stands right now — its PR, the CI roll-up, the review decision, the comment thread — then relay what is blocking it, or comment and close it out.
whenToUse: Use for a one-off READ of an issue or PR's current forge state and the writes that close it out — "is that PR green?", "did CI pass?", "what's blocking it?", "did anyone reply on that issue?", "why is this issue still open?", "what did the reviewer say?", "comment on it and close it". Covers checking CI or check status, reading a review decision, reading an issue's comment thread, forwarding forge-sourced blockers to the agent still working, and posting a closing comment. Do not use to leave something watching and wake the user on a LATER PR transition (use daintree.orchestration.watch-outcome); to commit, push, open or ready a PR (use daintree.workflow.prep-branch-for-review); to search or triage the backlog for new work (use daintree.workflow.find-issue-work); to start work on an issue (use daintree.workflow.start-work-on-issue); or to forward a review that is already sitting in a reviewer agent's terminal rather than on the forge (use daintree.agents.relay-review-feedback). Do not use to DIAGNOSE or FIX a failing check — reading that a check is red is here, working out why and getting it green is daintree.ci.diagnose-and-fix.

## daintree.workflow.prep-branch-for-review
title: Prepare a branch for review
summary: Get a read-only review-readiness verdict, then do the real prep — commit, push, open the PR — branching on what the verdict reports.
whenToUse: Use when the user asks to prepare a branch for review, open or ready a PR, wrap up work on an issue for review, or check whether the current branch is ready to push. Do not use to judge whether an agent's work is actually correct or complete before trusting it (use daintree.orchestration.verify-agent-work), to START work on an issue rather than finish it (use daintree.workflow.start-work-on-issue), to be notified later when the PR merges (use daintree.orchestration.watch-outcome), to read an EXISTING PR's CI or review state or to comment on and close its issue (use daintree.workflow.follow-up-on-issue), to forward a reviewer's findings to an implementer agent (use daintree.agents.relay-review-feedback), to REVIEW the change rather than ready it (use daintree.review.review-change), or to fix a failing check (use daintree.ci.diagnose-and-fix).

## daintree.workflow.start-work-on-issue
title: Start work on a forge issue
summary: How to pick a forge issue and start work on it through workflow.startWorkOnIssue or the explicit path, which spawns the agent and asks Daintree for a notice when it stops.
whenToUse: Use when the user asks to start work on ONE forge issue they have already settled on — pick up a ticket, begin an issue, set up a worktree/branch for it and put an agent on it. Do not use when the issue is NOT yet chosen and the job is searching or triaging the backlog for a candidate (use daintree.workflow.find-issue-work); for SEVERAL issues at once, an agent per ticket, or working a batch in parallel (use daintree.orchestration.fan-out-work); to finish work and open a PR (use daintree.workflow.prep-branch-for-review); to check CI, a review decision or the issue thread on work already underway (use daintree.workflow.follow-up-on-issue); for a change with no forge issue behind it (use daintree.edits.spawn-visible-agent); to create a worktree from a workspace recipe rather than an issue (use daintree.recipe.run-or-create); or to pick up / resume work already in flight from an earlier session (use daintree.orchestration.status-and-resume).

## daintree.worktree.create-plain-worktree
title: Create a plain Daintree worktree
summary: Create a standalone Daintree worktree for a new or existing branch with Daintree's own worktree creator, without launching a recipe or agent.
whenToUse: Use when the user asks to create, add, or set up a plain worktree for a new branch or an existing branch — "create a worktree", "make a new branch in its own worktree", or "check out this branch as a worktree" — and they do not want a recipe or agent launched. Do not use for a worktree with a workspace recipe (use daintree.recipe.run-or-create), for starting a forge issue with an agent (use daintree.workflow.start-work-on-issue), for spawning an agent into an existing worktree (use daintree.edits.spawn-visible-agent), for giving agents that are ALREADY RUNNING one worktree each (use daintree.worktree.relocate-agents), or for deleting a worktree (use daintree.orchestration.workspace-cleanup).

## daintree.worktree.manage-resource
title: Manage a worktree remote resource
summary: Inspect and interactively provision, pause or resume a worktree's configured remote resource, verifying with fresh status and refusing unsafe unattended or unpreviewed lifecycle actions.
whenToUse: Use when the user asks about a worktree's cloud devbox or remote resource status, wants to provision, pause or resume it, asks to save resource cost, or asks for a future pause/resume. Also use for teardown or connect requests so the assistant can route those unsupported-safe paths honestly. Do not use for creating or deleting an ordinary git worktree (use daintree.worktree.create-plain-worktree or daintree.orchestration.workspace-cleanup), Daintree's own CPU/memory resource profile, or starting a local dev server.

## daintree.worktree.provision-local-environment
title: Give each worktree its own database, port and local environment
summary: Diagnose checkouts colliding over one shared database, schema, port, docroot, container or dev server — migrations clobbering each other, a second copy failing to boot, one branch's seed data showing up in another — and get the project's worktree lifecycle setup and teardown scripts written so each worktree provisions its own stack and deleting it releases them.
whenToUse: Use for TWO related asks. First, a shared runtime resource that several worktrees collide over so branches cannot run side by side — "my worktrees all share one local site", "each branch needs its own database", "give every worktree its own URL", "two worktrees fight over port 3000". Second, configuring the project's worktree lifecycle scripts themselves — "add a setup script that runs when a worktree is created", "a teardown script to drop the database when I delete a worktree", "provision new worktrees automatically". The tell is a per-worktree RESOURCE (database, port, hostname, docroot, container) or the setup/teardown configuration that creates it. Do not use to move agents that are already running into separate worktrees (use daintree.worktree.relocate-agents), to create a worktree (use daintree.worktree.create-plain-worktree), to launch a worktree's startup terminals or dev server (use daintree.recipe.run-or-create), for a cloud devbox or remote resource (use daintree.worktree.manage-resource), or to RUN a test suite, check or command in a worktree that already works (that is an ordinary check run, not a provisioning problem).

## daintree.worktree.relocate-agents
title: Move running agents into their own worktrees
summary: Move agents that are ALREADY RUNNING into worktrees of their own: create the worktrees, file each terminal under its own, and tell each agent to continue, or start the task it was given, in its new directory.
whenToUse: Use when an agent that ALREADY EXISTS, one or several, idle or mid-task, is to be moved into its own new or another worktree, optionally with a task to do there — "move Claude to a new worktree called X and have it fix Y there", "move each of those into its own worktree", "create four worktrees and move the agents into them", "give each terminal its own branch", "isolate these agents so they stop colliding". The tell is that the terminals ALREADY EXIST; the user wants them relocated, not replaced. Do not use to create a worktree with no agent involved (use daintree.worktree.create-plain-worktree), to spawn NEW agents into fresh worktrees (use daintree.edits.spawn-visible-agent, daintree.orchestration.fan-out-work for a cohort, or daintree.orchestration.competition when each does the same task to be compared), to start a forge issue in a worktree (use daintree.workflow.start-work-on-issue), to create a worktree with a startup recipe (use daintree.recipe.run-or-create), or to delete worktrees (use daintree.orchestration.workspace-cleanup).
